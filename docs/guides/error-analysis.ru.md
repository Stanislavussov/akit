# Error Analysis: подробное руководство

Это руководство по экрану **Error Analysis** в AKit и по тому, что эта функция добавила на экраны **Lab** и **Settings**. Оно написано по коду, а не по замыслу: если кнопка делает что-то неожиданное, здесь сказано, что именно. Названия кнопок и полей даны по-английски, как на экране.

## Что это и как всё устроено
<!-- section: overview -->

### Зачем это нужно

Один разбор одной сессии отвечает на вопрос «что пошло не так здесь». Error Analysis отвечает на другие вопросы: что ломается снова и снова, как часто, на каком шаге работы и помог ли фикс. Каждое утверждение опирается на шаги настоящих транскриптов.

Метод взят у Hamel Husain и Shreya Shankar (error analysis для LLM-систем). Его суть:

- Сначала вы сами читаете сессии и пишете свои заметки. Модель в это время свои заметки вам не показывает.
- Модель пишет свободные заметки о проблемах в каждой сессии, без заранее заданных категорий.
- Заметки группируются в конкретные «режимы отказа» (modes): например, «прочитан целиком файл на 34 КБ», а не «проблемы с контекстом».
- Частота режима считается только по проверке (check), которая выносит вердикт «есть / нет» по каждой сессии. Не по заметкам.
- Новые сессии добавляют, пока не перестанут появляться новые режимы (насыщение).

Ваше суждение задаёт режимы и метки. Модели применяют его к большому числу сессий. Вы не размечаете каждую сессию: вы размечаете стартовый набор, подтверждаете изменения списка режимов и решаете спорные случаи.

### Весь конвейер одной картинкой

Для каждой сессии, которую разбирают (поштучно или в пакете), происходит одно и то же:

1. **Заметки (notes).** Один вызов модели. Модель не видит список режимов, поэтому заметки «слепые». Она получает дайджест транскрипта и пишет по порядку: требования задачи (из реплик пользователя), исход сессии (outcome), список заметок (описание, шаг `#n`, цитата из этого шага, серьёзность, слой вины, «корень или симптом», примерная цена), решающий и наблюдаемый шаг (decisive/observed step), абзац 3–5 предложений и не больше трёх советов.
2. **Проверка (verifier).** Сначала код проверяет каждую цитату: она должна быть не короче 8 символов (у цитаты с пропуском «…» — хотя бы одна её часть) и дословно найтись в указанном шаге (у цитаты с пропуском — все части по порядку; переносы строк и кавычки прощаются, слова нет). Затем второй вызов модели проверяет, подтверждает ли цитата утверждение. Проверяющая модель видит цитируемый шаг и по три шага до и после него. Для заметок высокой серьёзности она сначала пишет аргумент «проблемы здесь нет» (steelman), потом выносит вердикт. Отклонённые заметки хранятся с причиной, но в пул не попадают. Советы, все заметки которых отклонены, выбрасываются.
3. **Сопоставление (matching).** Отдельный вызов. На вход идут только принятые заметки и текущий список режимов (определения, критерии, примеры), без транскрипта. Пример из сессии, которую этому адресату слать нельзя, в вызов не идёт. Для каждой заметки модель выбирает один режим с уверенностью от 0 до 1 или явно отвечает «ничего не подходит» (none fits). Маршрут с уверенностью ниже 0.6 уходит вам на вкладку Review.
4. **Кластеризация (clustering).** Один вызов в конце пакета (или по кнопке) над заметками, которым не подошёл ни один режим. Он предлагает режимы-кандидаты (candidates). Кандидат никогда не подтверждается автоматически по результату кластеризации.
5. **Проверки (checks).** Отдельно от заметок. По каждому активному режиму есть проверка: код (mechanical или heuristic) или LLM-судья (judge). Только они дают частоты в отчётах.

Важное различие: заметки и сопоставление ведут список режимов (что бывает, примеры, кандидаты), но никогда не дают знаменатель. Частота режима в отчёте берётся только из его проверки, прогнанной по всем сессиям пакета. Если у режима нет проверки, которой можно доверять, отчёт пишет «seen in k notes» («встречен в k заметках») без процента.

### Откуда берутся данные

Всё строится на индексе сессий (`~/.akit/index/index.sqlite`). Это та же база, которую использует команда `akit sessions import`. Пакеты выбирают сессии из индекса, код-проверки бегут по всем сессиям индекса, а «до/после фикса» тоже считается по индексу. Если индекс пуст, почти ничего не работает. Как его заполнить, сказано в разделе о подготовке.

Сессии, которые сделал сам Lab (повторы коммитов, контрольные ячейки), из выборок, стартового набора и частот исключаются. Сами вызовы моделей для анализа запускаются без сохранения сессии (`--no-session-persistence` у Claude Code, `--no-session` у Pi), поэтому в индекс не попадают.

### Где что лежит в интерфейсе

- Боковая панель → **Error Analysis** (иконка стетоскопа). Вверху переключатель вкладок: **Modes**, **Review** (с числом ожидающих дел в скобках), **Bootstrap**, **Reports**, **Evals**. Справа в панели инструментов: **History** (история списка режимов), **Reload** (перечитать `~/.akit/lab/analysis`) и **Guide** (открывает это руководство). Число в скобках у **Review** видно, только когда очередь не пуста. Руководство открывается также кнопкой **Guide** в панели инструментов экрана **Lab**, кнопкой **How It Works** в Settings → **Sending policy** и из меню Help → **Error Analysis Guide**.
- Под панелью инструментов появляется полоса состояния: синяя с индикатором, пока что-то считается («Checking 120 of 900 sessions…»), зелёная с итогом последнего действия, оранжевая с ошибкой. У зелёной и оранжевой есть крестик **Dismiss**.
- Экран **Lab**: здесь живут все запуски, которые идут в терминале или в фоне. Пакеты анализа, разборы отдельных сессий и контрольные ячейки — это всё Lab-запуски. Там же вкладка **Sends** — журнал всех отправок данных моделям.
- **Settings** (⌘,) → раздел **Lab** и ниже: политика отправки, учётные записи Pi, маскирование, месячный лимит.
- Экран **Sessions** → кнопка с колбой **Review in Terminal…** у сессии Claude Code или Pi (подсказка «Lab: an agent reviews this session in a terminal tab and writes what to change»): разбор одной сессии. Рядом кнопка со слоями **Add to Layer Set…**: контрольная задача из этой сессии в набор слоя (см. «Вкладка Evals»).

### Что AKit никогда не делает

- Не меняет ваши настоящие сессии, `CLAUDE.md`, скиллы и хуки. Фиксы вы применяете сами. AKit только записывает момент применения.
- Не читает ключи харнессов. Аккаунт Claude Code он узнаёт через `claude auth status --json`. Аккаунт Pi узнать нельзя, и для разбора сессии тем же провайдером он не нужен.
- Не отправляет ничего мимо политики отправки. Все вызовы моделей анализа идут через одну точку, где проверяются политика, маскирование, лимит и где пишется журнал. Запуски агентов (контрольные ячейки, разборы **Agent with file tools**, повторы коммитов) идут иначе: та же проверка политики, но маскируется только промпт или транскрипт (код репозитория нет), лимит сверяется только с уже потраченным, а у агента есть инструменты.
- Код-проверки работают локально и ничего не отправляют.

## Перед началом: настройки, индекс, деньги
<!-- section: start -->

### Нужна команда akit

Все запуски Lab (разборы, пакеты, контрольные ячейки) выполняет команда `akit lab run ID` во вкладке терминала или в фоне. Если `~/.local/bin/akit` нет или она старше приложения, кнопки постановки в очередь выдадут ошибку «The akit command is not installed» или «… is older than this AKit». Тогда в папке AKit выполните:

```
make install-cli
```

### Заполните индекс сессий

В приложении нет кнопки импорта сессий в индекс. Это делается командой:

```
akit sessions import
```

Она читает логи Claude Code и Pi, кладёт сессии в индекс и привязывает их к проектам. Если анализ уже используется (существует список режимов), сразу после импорта она же пересчитывает дешёвые сигналы и прогоняет код-проверки активных режимов по новым сессиям. Это локально и бесплатно.

Чтобы импорт шёл сам каждый час и чтобы записывался HEAD репозитория в начале каждой сессии, поставьте захват:

```
akit insights install --yes
```

Для хука Claude Code нужен репозиторий мозга (brain): плагин хранится в нём. Без мозга команда откажет; тогда поставьте только части Pi и launchd (`akit insights install --only pi --yes`, `--only launchd`) или сначала создайте мозг (`akit init`).

> **Важно:** HEAD в начале сессии записывает только хук захвата. Без него сессию нельзя превратить в контрольную задачу (вкладка Evals). Сессии, начатые до установки хука, тоже нельзя: для них пишут «минимальное воспроизведение».

### Проверьте, какой это Mac

Settings → **This Mac**: **Personal** или **Work**. От этого зависит политика отправки:

- На обоих Mac действует правило «тот же источник» (same origin). Сессия Claude Code может уйти в Claude Code под тем аккаунтом, что вошёл сейчас (транскрипт аккаунт не хранит, сравнивается только харнесс). Сессия Pi может уйти в Pi через того же единственного провайдера, через которого шла. Ничего вводить не нужно. Всё остальное добавляется в список разрешённых явно. Ограничение: AKit не видит, под каким аккаунтом записана сессия. Если после сессии вы вошли в агента под другим аккаунтом (например, на рабочем Mac — в личный Claude), разбор уйдёт в новый аккаунт. На рабочем Mac работайте в агентах только под рабочими аккаунтами.
- **Work**: список составляйте по правилам компании, по умолчанию он пуст. Код репозитория (повторы коммитов и контрольные запуски) на рабочем Mac уходит только адресатам из списка.
- **Personal**: код репозитория может уйти и в тот агент, которым вы с ним работаете.

### Настройте политику отправки

Settings → **Sending policy**. Подробно каждая кнопка описана в разделе о настройках. Минимум на старте:

1. Нажмите **Check Accounts**. AKit спросит Claude Code и Pi, через какой аккаунт пойдёт разбор сейчас, и покажет, можно ли туда слать их собственные сессии.
2. Сессию можно без списка вернуть тому агенту и провайдеру, который её записал, на любом Mac. Для остального (например, сессий Claude Code через Copilot в Pi) нажмите **Add to List** у аккаунта, которому можно отдавать данные сессий; на рабочем Mac — только по правилам компании.
3. Для Pi ничего вводить не нужно, если Pi уже вошёл к провайдеру: сессия уходит тому провайдеру, который её записал, на любом Mac. Запись нужна, только чтобы отправлять в Pi чужие данные (например, сессии Claude Code через `github-copilot`): **Add Destination…** → **Harness** Pi, провайдер, ваш логин и организация. Эта же запись становится аккаунтом Pi для провайдера.
4. В **Masked before sending** добавьте шаблоны внутренних хостов и оставьте включённым **Mask e-mail addresses**.
5. В **Cost** задайте **Monthly limit (US dollars)**.

> **Почему так:** правило «тот же источник» значит, что сессию Claude Code на личном Mac можно разбирать через Claude Code без настройки. А вот разбор той же сессии через Pi и GitHub Copilot — это отправка данных другому провайдеру, и её надо разрешить явно.

### Выберите одну модель для заметок и держитесь её

Качество заметок (полнота, точность, совпадение фаз) меряется отдельно для каждой «версии заметок»: харнесс + модель + версия промпта, например `claude-code · opus · notes v1`. Матрица переходов в отчётах показывается только если для версии заметок пакета есть замеры стартового набора. Если вы разметили стартовый набор с одной моделью, а пакеты гоняете другой, отчёты будут без полноты и без матрицы.

> **Совет:** выберите модель для заметок один раз (например, ту, что стоит по умолчанию в Claude Code) и используйте её и в **Queue Model Notes…**, и в пакетах. Язык разбора тоже входит в ключ заметок: смена языка заставит переписать заметки.

### Сколько это стоит и откуда цифры

AKit не знает тарифов и не считает цены по токенам. Он берёт только то, что записал сам харнесс: `total_cost_usd` у Claude Code и `usage.cost.total` у Pi. Каждый вызов попадает в журнал `~/.akit/lab/analysis/sends.jsonl` (экран Lab → **Sends**).

Отсюда следствие: пока вы ни разу не вызывали выбранную модель, оценки нет («no estimate yet»). Чтобы получить первую оценку, разберите одну сессию этой моделью: после этого окна отправки и форма пакета покажут «≈ $…» для того же харнесса и той же модели (имя модели должно совпадать точно). Оценка ячеек появится после первой контрольной ячейки этой модели (а до неё — после первого реплея этой модели в Lab). Для оценки слоя в Brain → **Evaluate…** первые ячейки можно поставить отдельно: **Queue 2 Calibration Cells…**, по одной ячейке каждой настройки (см. «Наборы слоёв»). Подробно о деньгах — в отдельном разделе.

## Первые шаги: как пройти путь правильно
<!-- section: first-steps -->

Ниже рекомендуемый порядок на первый день и первую неделю. Он повторяет логику метода: сначала вы, потом модель; сначала список режимов, потом частоты; сначала критерий «помогло», потом фикс.

### День 0: подготовка (30–60 минут)

1. Установите `akit` (`make install-cli`), если её нет.
2. Выполните `akit sessions import`. Если хотите, чтобы индекс обновлялся сам и записывался HEAD, выполните `akit insights install --yes`.
3. Settings → **This Mac**: проверьте Personal/Work.
4. Settings → **Sending policy**: **Check Accounts**, **Add to List** для адресатов чужих данных (для Pi — **Add to List…**: спросит логин и организацию), шаблоны маскирования, **Monthly limit**.
5. Выберите модель для заметок (см. предыдущий раздел).

### День 1: пробный разбор одной сессии ради цены

1. Экран **Sessions** → выберите длинную сессию Claude Code (5+ запросов).
2. Кнопка с колбой **Review in Terminal…** → в окне выберите **Harness**, **Model**, **Effort**, **How** = **One model call** → **Queue and Start**.
3. Экран **Lab** покажет запуск. Когда он закончится, вы увидите исход, требования, заметки (принятые и отклонённые), советы.
4. Lab → **Sends**: посмотрите, сколько стоили вызовы `notes`, `verifier` и `matching`.

> **Почему так:** после этого форма пакета и окна отправки показывают оценку в долларах для этого харнесса и этой модели. Без записанного вызова этой модели оценки нет вообще. Сессия, разобранная моделью, больше не попадёт в стартовый набор: AKit не берёт туда сессии, заметки которых вы могли видеть.

> **Важно:** в анализ попадают только разборы в режиме **One model call**. Режим **Agent with file tools** — это старый разбор Lab: он пишет абзац и советы, но не создаёт заметок и ничего не добавляет в пул.

### Дни 1–3: стартовый набор (bootstrap), самое важное

1. Error Analysis → **Bootstrap** → **Pick Sessions…** → оставьте 30 → **Reserve**. AKit выберет сессии из индекса: половина — представители групп «проект × слой» (харнесс | семейство модели | сильнейший сигнал), остальные случайные. Эти сессии сразу резервируются: поштучный разбор их не возьмёт, пока вы их не разметите, а пакеты не возьмут никогда, даже после разметки.
2. Откройте первую сессию в списке слева. Читайте транскрипт. Для каждой проблемы: нажмите номер шага, выделите цитату в окошке, напишите, что пошло не так, **Add Note**. В конце задайте **Outcome** и примерный решающий шаг. **Finish…** и **Finish** в окне подтверждения. Если прервались, **Save Draft**.
3. Повторите для всех 30. Сессия без проблем — тоже полноценная метка: просто задайте исход и нажмите **Finish…**.
4. **Queue Model Notes…** → выберите ту же модель, что будет у пакетов → **Queue N Sessions**. В Lab появится один пакет «Bootstrap: model notes on N labeled sessions».
5. Когда он закончится, для каждой размеченной сессии: **Propose Pairs…** → **Send** → проверьте пары, отметьте **A real problem** у заметок модели, с которыми согласны → **Confirm**. В обзоре **Metrics and Mapping** появятся полнота и точность.
6. **First Modes…** → **Send**. Модель сгруппирует ваши и свои заметки в кандидатов.
7. Вкладка **Review** → **Candidate modes**: подтвердите настоящие и конкретные (**Confirm**), переименуйте (**Rename…**), слейте дубликаты (**Merge into…**), отклоните мусор с причиной (**Reject…**).
8. Вкладка **Modes**: посмотрите девять «семян» (seeds) — режимов из исследований и наших наблюдений. Если вы видели такие проблемы в своей разметке, подтвердите их (**Confirm**).
9. Вернитесь в **Bootstrap** → **Metrics and Mapping** → **Your notes → modes**: каждой своей заметке выберите режим или **Unclear**.
10. Для каждого режима с вашими заметками нажмите **Find Similar Cases…** и примите или отклоните каждую находку.

> **Почему так:** выборочная проверка заметок модели показывает только точность (не выдумала ли модель проблему). Полноту (что модель пропустила) видит только человек, который сам прочитал транскрипт. Поэтому вы размечаете первым и вслепую. Полнота — главный риск, и это единственное место, где она меряется.

> **Важно:** разметьте все свои заметки в сопоставлении. Отрицательной меткой для режима сессия становится, только когда все ваши заметки в ней сопоставлены (с другими режимами или с **Unclear**). Пока хоть одна не сопоставлена, сессия даёт только положительные метки режимам уже сопоставленных заметок, а отрицательных не даёт вовсе.

### Неделя 1: пакеты и насыщение

1. Экран **Lab** → **New Run…** → **Error Analysis Batch**. Выберите проект или **All projects**, период, **Sessions** = 20, **Notes by** (та же модель, что в стартовом наборе, через **Choose…**, или **Automatic**). Посмотрите оценку внизу формы. **Sample and Queue**.
2. Пакет идёт по две сессии одновременно. В Lab видно продвижение по шагам. Его можно остановить (**Pause**) и продолжить (**Resume**).
3. Когда пакет закончится, в Lab нажмите **Open Report**. Если вы всё это время держали экран Error Analysis открытым, нажмите там **Reload**: сам он перечитывается только после поштучных разборов. Отчёт откроется на вкладке **Reports**.
4. Вкладка **Review**: кандидаты, маршруты с низкой уверенностью, выборочные проверки (spot checks), «зонтичные» семена. Разберите всё.
5. Повторяйте пакеты. В отчёте смотрите блок **Saturation**: если доля заметок без режима и число новых режимов несколько пакетов подряд около нуля, список насыщен.

> **Совет:** по возможности продолжайте размечать стартовые сессии, пока счётчик «Since the list of modes last changed» на вкладке Bootstrap не станет зелёным (20 размеченных сессий без изменений списка). Это правило остановки стартовой разметки.

### Неделя 2: проверки, фикс, оценка

1. На **Modes** выберите частый режим. Если у него есть код-проверка, нажмите **Run Check** и посмотрите долю по всем сессиям индекса.
2. **Draft Fix…**: слой (правило `CLAUDE.md`, скилл и т. п.), текст фикса, что должно измениться в транскриптах, критерий «помогло». Сохраните до любых запусков.
3. Если режим в тройке самых частых или самых дорогих и у него есть черновик фикса, можно включить судью (**Enable Judge…**). Проверьте его на dev (**Validate on Dev…**), доведите до приемлемого, затем один раз на test (**Validate on Test…**).
4. Примените фикс сами (отредактируйте свой `CLAUDE.md` или скилл).
5. **Mark Applied…** с моментом, когда изменение попало в вашу настройку. Это точка T.
6. Работайте как обычно. Импорт (`akit sessions import` или hourly-агент) прогоняет код-проверки по новым сессиям. Когда с каждой стороны от T будет 15+ сессий, блок **Before and after T** даст вердикт.
7. По желанию: вкладка **Evals** → контрольные задачи → **Run Cells…** с базой и вариантом. Это сильнее, чем «до/после», потому что набор задач не меняется.

## Вкладка Modes
<!-- section: modes -->

Верхняя половина — таблица режимов. Нижняя — страница выбранного режима (описана в следующем разделе). Граница между ними перетаскивается.

### Что такое режим

Режим (mode) — это шаблон с определением и критериями, а не просто имя. У него есть:

- **id** — постоянный slug, переживает переименования. Результаты и примеры привязаны к нему.
- **Name** — конкретное название.
- **Kind**: `failure` (отказ), `efficiency` (лишняя трата времени или токенов), `success` (стратегия, которая сработала).
- **Definition** — 1–2 предложения.
- **Include** / **Exclude** — критерии для пограничных случаев.
- **Origin**: `seed (studies)` — семя из опубликованных исследований, `seed (ours)` — семя из наших наблюдений, `emergent` — найден в ваших заметках.
- **Scope**: `general` или `project:<id>`.
- **Version** — растёт при любом изменении смысла (определение, критерии, вид, слияние, разделение).
- **Status**: `seed, inactive`, `candidate`, `active`, `rejected`; слитый режим показывается как `merged`.

Режимы никогда не удаляются. Отклонённый режим остаётся с причиной, чтобы модель не предлагала его снова. Слитый остаётся со ссылкой на режим, в который его слили, и его старые результаты пересчитываются через эту ссылку.

### Девять семян

При первом обращении AKit создаёт список и кладёт в него девять семян в статусе `seed, inactive`:

1. Overclaiming completion — заявлено «готово», хотя ничего это не подтвердило, или ошибка инструмента скрыта.
2. Explicit user constraint violated — нарушено явное ограничение пользователя.
3. Intent misread on an underspecified request — неоднозначный запрос прочитан не так, без вопроса.
4. Scope overreach — изменения вне запроса без согласия.
5. Weakening tests or oversight — тесты или проверки ослаблены, чтобы пройти.
6. False premise / wrong diagnosis — действие на непроверенном неверном предположении.
7. Steps repeated without progress — одно и то же действие 3+ раз без новой информации.
8. A long session not reset after finished steps (efficiency) — после законченных шагов новая работа в том же большом контексте.
9. A large file read whole (efficiency) — файл больше 20 КБ прочитан целиком.

Неактивное семя участвует в сопоставлении (заметки могут на него попадать), но не появляется в отчётах и не может получить судью. Его код-проверка (если она есть) не запускается сама ни при импорте, ни в конце пакета, но ручной **Run Check** работает, и колонка **Code check** её показывает. Семя становится активным в двух случаях: вы нажали **Confirm**, или два разных пакета своим сопоставлением отнесли к нему заметки из двух разных сессий (считаются и маршруты с низкой уверенностью, которые вы ещё не рассматривали).

### Переключатель Current / All

- **Current** — режимы, которые не слиты и не отклонены.
- **All** — все режимы, когда-либо созданные.

Рядом счётчик: «N modes · K notes fit none» — сколько принятых заметок пула сейчас имеют маршрут «ничего не подходит». Заметки совсем без маршрута сюда не входят. Это материал для кластеризации.

Справа кнопка **Run All Checks** — то же, что `akit analysis check` без режима: код-проверки всех текущих режимов, у которых они есть (и неактивных семян тоже), за один проход по индексу, прямо на Mac, ничего не отправляет. Прогресс в синей полосе; пока идёт любая проверка, кнопка серая.

### Колонки таблицы

- **Name** — при наведении показывается определение.
- **Status** — цветная плашка: зелёная `active`, оранжевая `candidate`, серая `seed, inactive` и `merged`, красная `rejected`.
- **Kind**, **Origin**, **Scope**, **Ver.** — см. выше.
- **Seen in** — «N notes»: сколько принятых заметок модели из всего пула сейчас относятся к режиму (после слияний). Маршруты с низкой уверенностью считаются только после того, как вы их приняли. Ваши собственные заметки стартового набора сюда не входят.
- **Code check** — если у режима есть код-проверка: «k of n (95% a–b%)» по всем сессиям индекса и тип проверки: `mechanical` или для эвристической её настоящий уровень доверия по тестовому прогону этой версии режима — `heuristic — validated`, `heuristic — provisional` или `heuristic — not validated`. «not run» — проверку ещё не запускали. Прочерк — код-проверки нет.

Сортировка: сначала активные, потом кандидаты, неактивные семена, отклонённые, слитые.

> **Важно:** колонка говорит о самой код-проверке. Если у режима включён судья, отчёты берут судью, и его доверие показывает плашка рядом с заголовком **Judge & validation** на странице режима.

### Контекстное меню строки

Правый клик по строке даёт те же действия, что кнопки на странице режима: **Confirm**, **Rename…**, **Edit…**, **Scope…**, **Merge into…**, **Split…**, **Reject…** или **Restore**. Они описаны в следующем разделе. **Retro-match…** в меню нет, только на странице режима.

### Кнопки панели инструментов

- **History** — список коммитов локального git-репозитория режимов: каждое изменение списка, когда оно было. Только чтение.
- **Reload** — перечитать всё из `~/.akit/lab/analysis`. Нужна, если вы что-то меняли через `akit` в терминале. Экран сам перечитывается после своих действий, после каждого законченного поштучного разбора, пакета и контрольной ячейки, а пока пакет идёт — после каждого шага любой его сессии.

Состояние экрана живёт, пока открыто приложение: если уйти в другой раздел и вернуться, список «The notes missed …» судьи и блок «Clustered from scratch» на Reports остаются на месте. Пропадают они только при перезапуске AKit.
- **Guide** — открывает это руководство.

## Страница режима
<!-- section: mode-page -->

Страница открывается под таблицей, когда вы выбираете режим. Сверху вниз: заголовок с действиями, определение, код-проверка, судья и валидация (только у активных), фикс (только у failure и efficiency), примеры (exemplars), заметки режима.

### Заголовок

Название, плашка статуса и строка «id · kind · origin · scope · vN». Под ними кнопки действий.

### Confirm

Есть у кандидатов и неактивных семян. Делает режим активным:

- в `modes/modes.json` статус становится `active`, записывается дата подтверждения, в локальном git-репозитории режимов появляется коммит «Confirm mode …»;
- если у режима есть код-проверка, она сразу бежит по всем сессиям индекса (локально, бесплатно, с прогрессом в полосе состояния); если в этот момент уже идёт другая проверка, полоса пишет «… is active. Its code check starts when the one running now is done.», и проверка режима начнётся сама, когда та закончится;
- на странице появляется зелёная плашка с предложением следующих шагов: **Retro-match the Note Pool…** и, если у режима есть код-проверка, **Run Check**. Проверка уже запущена подтверждением, поэтому, пока она идёт, кнопка серая, а когда закончится, вместо неё видно «Checked: k of n (95% a–b%)».

После подтверждения режим появляется в отчётах и может получить судью. Подтверждение меняет список режимов, поэтому сбрасывает счётчик правила остановки стартовой разметки.

> **Совет:** подтверждайте только конкретные режимы. «Агент читает лишнее» — плохо. «Файл больше 20 КБ прочитан целиком без диапазона» — хорошо. Широкий режим потом придётся делить, а деление сбрасывает валидацию.

### Rename…

Новое имя. Id не меняется, поэтому результаты, примеры и метки остаются привязанными. Версия не растёт, валидация не сбрасывается. Коммит в репозитории режимов. Имя не может совпадать с именем другого текущего режима.

### Edit…

Окно с полями **Kind**, **Definition**, **Include**, **Exclude** (по одному критерию на строку). Любое изменение этих полей:

- поднимает версию режима на 1;
- делает недействительными результаты валидации (они привязаны к версии) и код-проверки (у неё записана версия режима, страница предупредит «Made for vN; the mode is vM now. Run it again.»);
- меняет ключ сопоставления, поэтому следующее сопоставление сессий пройдёт заново (это вызов модели);
- делает коммит.

Если смена вида делает режим успешным (`success`), его фикс сбрасывается. У слитого режима кнопки нет: правьте тот, в который его слили.

> **Почему так:** критерии — это то, что модель применяет. Изменили критерии — значит, проверка теперь меряет другое. Старые TPR и TNR к новой версии не относятся.

### Scope…

**General** или **One project** с id проекта (меню **Projects** подставляет проекты из мозга). Версия не меняется. Коммит.

Область действует только в отчётах: режим одного проекта считается только по сессиям этого проекта в пакете, а в отчёте пакета, где таких сессий нет, его нет вовсе. Сопоставление, проверки и судьи по-прежнему видят все режимы.

### Merge into…

Выберите целевой режим из текущих. Этот режим получает отметку «слит в …» и уходит из текущего списка. Его заметки теперь считаются за целевой. Версия целевого режима растёт (его валидация сбрасывается). Коммит. Отменить слияние кнопкой нельзя.

### Split…

Введите минимум две части: имя и определение каждой (**Add Part** добавляет ещё). Новые режимы создаются как кандидаты версии 1 с тем же происхождением. Старый режим остаётся, но становится отклонённым с причиной «split into …», его версия растёт. Коммит. Заметки старого режима сохраняют маршрут к старому, теперь отклонённому режиму. **Retro-match…** по каждому новому режиму только предложит им второй маршрут «also fits» (уверенность ниже 0.6), который вы принимаете на вкладке Review. Заново заметки сопоставятся, только когда сессию разберут ещё раз (пакет, **Queue Model Notes…**, `akit analysis route`).

### Reject… и Restore

**Reject…** требует причину («Rejected because…»). Режим остаётся в списке со статусом `rejected`, а его имя попадает в список «не предлагать» для кластеризации. Коммит. Заметки, уже отнесённые к отклонённому режиму, так и остаются за ним: они не возвращаются в «fit none» и не кластеризуются заново.

**Restore** у отклонённого режима возвращает его: подтверждённый ранее становится активным, семя — неактивным семенем, остальные — кандидатами. Коммит.

### Retro-match…

Есть у всех текущих режимов. Открывает окно отправки (о нём ниже, в разделе о деньгах). Что происходит:

- все принятые заметки пула (всех разобранных сессий) идут модели пачками по 60 вместе с определением и критериями этого режима;
- модель отвечает по каждой: подходит или нет, с уверенностью;
- заметка, у которой режима не было, переезжает в этот режим (маршрут источника `retro`); если уверенность ниже 0.6, маршрут ждёт вас на вкладке Review;
- заметка, которая уже относится к другому режиму, получает второй маршрут «also fits» с уверенностью ниже 0.6 — он ждёт вашего решения на Review и пока ничего не меняет (**Accept** перенесёт заметку в этот режим, из старого она уйдёт);
- затем AKit проверяет кандидатов: кандидат, получивший заметку из новой сессии, становится режимом.

Это вызов модели: стоит денег, идёт через политику. Используйте сразу после подтверждения нового режима, чтобы найти его в уже разобранных сессиях. Не нужно гонять его после каждого пакета: новые сессии и так сопоставляются со всеми режимами.

### Определение и критерии

Под заголовком: определение, списки **Include** (зелёные плюсы) и **Exclude** (красные минусы), причина отклонения, ссылка на режим слияния с кнопкой **Show**, строка «Fix: …» со статусом фикса. У успешного режима вместо неё: «A success mode: a strategy to keep, so it takes no fix».

### Code check и Run Check

Код-проверки есть только у пяти семян:

- **A large file read whole** — механическая (`mechanical`). Ищет Read без offset/limit или голый `cat` одного файла, вернувший больше 20 КБ, если тот же файл потом не перезаписан целиком.
- **Steps repeated without progress** — эвристическая. Один и тот же вызов с тем же результатом 3+ раз, кроме опроса (`sleep`, `watch`, `gh run`, статусы).
- **Overclaiming completion** — эвристическая. Финальный отчёт говорит «готово», а после последней правки не было теста, сборки или проверки, или «готово» сразу после ошибки инструмента.
- **Weakening tests or oversight** — эвристическая. Правка тестового файла уменьшает число тестов или проверок либо добавляет skip.
- **A long session not reset after finished steps** — эвристическая. Коммит, затем новый запрос пользователя и ещё 5+ вызовов инструментов в сессии, где контекст перевалил за 100K токенов.

**Run Check** прогоняет проверку по всем сессиям индекса (кроме лабораторных) прямо на Mac, ничего не отправляет. Пока горит синяя полоса прогресса (эта или любая другая проверка), кнопка серая.

Строка под описанием проверки говорит, что значит её доля сейчас: «Mechanical: …» — это и есть частота; «Heuristic — validated on the test set: …» — отчёты показывают долю с поправкой на ошибки проверки; «Heuristic — provisional …» — доля показывается рядом с «seen in k notes», но не как частота; «Heuristic — not validated: …» — частота режима «seen in k notes». Если у режима есть судья, добавляется «The mode has a judge: reports go by the judge's validation, not this one». Сессия, файл которой не менялся с прошлого раза, пропускается. Результат пишется в `checks/<mode-id>.json`. На странице появляется «Over indexed sessions: k of n (95% a–b%)».

- Механическая проверка — это и есть определение режима. Её доля по индексу и есть частота режима, без поправок.
- Эвристическая проверка только приближает режим. Пока её не провалидируют, частота режима — «seen in k notes», а доля проверки — просто ориентир.

Импорт сессий (`akit sessions import`) и конец каждого пакета сами прогоняют код-проверки активных режимов. **Confirm** на странице режима тоже запускает проверку сразу. Нажимать **Run Check** нужно после правки определения, перед валидацией эвристической проверки и у неактивных семян, если хотите увидеть их долю.

### Judge & validation

Блок есть только у активных текущих режимов. Рядом с заголовком плашка доверия к проверке: `exact` (механическая), `validated`, `provisional` или `not validated`.

**Enable Judge…** / **Change…** открывает окно выбора судьи: **Harness**, **Model**, **Effort** (у Pi — **Thinking**). У **Change…** в полях сразу стоит текущий судья. **Save** записывает судью в `labels/judges.json` и сереет, пока сохранение идёт. Судья — это LLM, который по дайджесту транскрипта решает, есть ли режим в сессии, отмечает шаги, «сложный случай» (tough call) и «серьёзно» (severe).

**Enable Judge…** и **Change…** доступны, только если режим среди активных в тройке лучших по «seen in k notes» или по цене (по сумме токенов или по сумме шагов, которые записаны в его заметках) и у него есть фикс в статусе `draft` или `applied`. Иначе под ними пояснение «Only a mode in the top 3 by notes or by cost …». **Disable**, **Run Judge over the Pool…** и кнопки валидации этим правилом не ограничены. Включённый судья продолжает работать в пакетах, даже если режим потом выпал из тройки. **Save** в окне судьи для Claude Code требует заполненного **Model**.

> **Почему так:** судья стоит денег на каждой сессии каждого пакета, а валидация требует около 100 меток на режим. Поэтому судья положен только тем режимам, которые часты или дороги и которые вы реально собираетесь чинить.

Что меняется после включения судьи:

- каждый следующий пакет вызывает судью на каждой своей сессии (строка **Judges** в Lab, плюс к оценке стоимости);
- в отчётах частоту этого режима теперь даёт судья, а не код-проверка;
- код-проверка режима продолжает работать, но в отчёт и в «до/после» идёт судья.

**Disable** убирает судью из `judges.json`. Режим возвращается к код-проверке или к «seen in k notes». Вердикты судьи остаются в файле `checks/<mode-id>@judge.json`.

**Run Judge over the Pool…** — окно отправки (судья фиксирован, выбирать модель не нужно). Судья судит каждую разобранную сессию пула (один вызов на сессию, дайджест до 360K символов, около 90K токенов, а для моделей с большим окном до 1M символов; секреты замаскированы). Сессии с неизменным файлом при том же судье, той же версии режима и той же версии маскирования пропускаются. Сессию, у которой реплики пользователя и ошибки инструментов одни не влезают в бюджет модели судьи, судья не получает: она остаётся без вердикта с ошибкой «too long for one judge call». Окно заранее считает такие сессии (кнопка на миг сереет) и пишет «Judges N of M reviewed sessions …; K judged before on an unchanged file are skipped and cost nothing»: размер и оценка «≈» — только по тем, что реально уйдут. После этого видно «Over the pool: present in k of n» и список «The notes missed N of the judge's finds» — сессии, где судья нашёл режим, а ни одна заметка туда не попала (показываются первые 12 и «and N more»). Это показывает, сколько упускают заметки. Список нигде не сохраняется: он держится, пока открыто приложение (переход в другие разделы его не стирает), и пропадает при перезапуске.

**Validate on Dev…** и **Validate on Test…** считают TPR и TNR проверки на ваших метках:

- Метки собираются автоматически (см. «Labels» ниже) и при каждом запуске валидации раскладываются по хешу сессии: 10% train, 30% dev, 60% test. Сессия, однажды попавшая в набор, там остаётся; новые метки раскладываются заново. Сессии примеров при каждом запуске переносятся в train.
- Если судья включён, кнопка открывает окно отправки: судья судит сессии набора (это вызовы модели). Уже осуждённые тем же судьёй на неизменённом файле пропускаются. Вердикты пишутся в `checks/<mode-id>@judge.json` и дальше считаются и в отчётах, и в «до/после». Если судьи нет, а проверка эвристическая, валидация идёт сразу, без отправки: берутся вердикты код-проверки по индексу.
- Результат пишется в `labels/validation.json` и показывается карточкой **Dev** или **Test**: TPR и TNR, нижняя граница Wilson (зелёная, если ≥ 80%), число меток «present» и «absent», сколько сложных случаев оставлено в стороне и сколько меток без вердикта.
- **Validate on Test…** можно нажать один раз на версию режима и проверку. После этого кнопка серая с пояснением. Новый тест разрешает только смена версии режима, харнесса или модели судьи, промпта судьи или версии код-проверки.
- Без судьи, у эвристической код-проверки, **Validate on Test…** сначала спрашивает «Validate on the test set?»: тест идёт один раз на эту версию и проверку, его TPR и TNR решают, насколько проверке верить. Кнопка **Validate on Test** в этом окне запускает, **Cancel** — нет. С судьёй подтверждением служит окно отправки.
- Пока у эвристической код-проверки нет результатов для текущей версии режима, обе кнопки валидации серые с пояснением «Run the code check for vN first: validation reads its verdicts». Иначе у меток не было бы вердиктов и единственный тестовый прогон пропал бы. Порядок: **Run Check**, потом **Validate on Dev…**, и только потом тест.

У механической проверки без судьи блока валидации нет: «Exact by construction: TPR = TNR = 1 against the definition».

Строка **Labels** внизу: всего меток, сколько «есть» и «нет», и по источникам: bootstrap (ваши заметки, сопоставленные с режимами), similar cases (принятые и отклонённые находки), tough calls (решённые сложные случаи). Ниже разбиение train/dev/test или «Not split yet».

### Fix

Блок есть у режимов `failure` и `efficiency`, пока режим текущий (в том числе у неактивных семян и кандидатов). Справа от заголовка статус фикса: `open: no draft yet`, `draft`, `applied at … (T)`, `confirmed`, `didn't help`, `rejected`.

**Draft Fix…** (или **Edit Draft…**) открывает окно черновика:

- **Layer**: CLAUDE.md rule, AGENTS.md rule, Skill (с полем имени папки скилла), Hook, Tool description, Environment. Для Hook, Tool description и Environment окно предупреждает: такой фикс нельзя опробовать на контрольных задачах, судить будут только сигналы из реальной работы.
- **Text** — сам текст фикса.
- **Expected change in transcripts** — что вы должны увидеть в транскриптах, когда фикс работает.
- **Helped when** — критерий «помогло». По умолчанию: «P(after < before) ≥ 0.95 on the mode's check, 15+ sessions a side, and no more than 50% that it got worse».
- **Exemplar notes** — галочки у заметок этого режима, на которые фикс опирается.

**Save Draft** серая, пока не заполнены **Text**, **Expected change in transcripts**, **Helped when** (и папка скилла для слоя Skill). Она пишет `fixes/<mode-id>.json` и ставит статус `draft`. Коммит в истории режимов получает только смена статуса: папка `fixes/` вне git. Ничего в ваших файлах не меняется.

> **Почему так:** критерий «помогло» записывается до любого запуска. Если придумывать его, глядя на результат, легко подогнать вывод под желаемое.

**Mark Applied…** (есть, когда черновик есть, а T ещё нет) — окно с датой и временем **Applied at**. Укажите момент, когда изменение реально попало в вашу настройку. Сессии, начатые раньше, считаются «до», остальные «после». Статус `applied`, записывается T, коммит. T ставится один раз.

**Confirmed**, **Didn't Help**, **Rejected…** появляются после применения. Они просто записывают ваше решение в статус фикса (коммит). **Confirmed** и **Didn't Help** сначала спрашивают подтверждение («Mark the fix as confirmed?» / «Mark the fix as didn't help?»). **Rejected…** просит причину. Вердикт блока «Before and after T» они не проверяют: решение за вами.

**Start Over…** — так называется кнопка сохранения в окне черновика, если фикс уже применён или закрыт. После подтверждения фикс возвращается в `draft`, T удаляется, «до/после» начнётся с нового **Mark Applied…**. Поле **Helped when** остаётся заполненным старым критерием: сохраняется то, что стоит в окне, поэтому перепишите его, если нужно.

**Try on Control Tasks…** есть, когда слой черновика — файл в репозитории (CLAUDE.md, AGENTS.md, скилл). Открывает окно **Run Cells** с вариантом «A mode's fix draft»: черновик дописывается в этот файл в каждом клоне. Серая, если контрольных задач ещё нет. Подробно — в разделе Evals.

**Before and after T** появляется после применения. Он берёт проверку режима (судью, если включён, иначе код-проверку) по сессиям индекса и сравнивает два окна: после T до сейчас и столько же времени до T (минимум сутки). Лабораторные сессии исключены. Учитываются только сессии, у которых есть вердикт проверки. Показывается:

- полоски «Before T» и «After T»: «k of n sessions (95% a–b%)», модель и версия харнесса, которые чаще всего были в периоде;
- плашка вердикта: `helped`, `not shown` или `no conclusion`;
- P(after < before), P(after > before), p Фишера;
- «With these numbers only a drop to about X% or lower would show (80% power)» — минимальный заметный эффект;
- предупреждения: сменилась модель сессий, сменилась версия харнесса (а с ней системный промпт), проверка не провалидирована;
- «Higher failure rate after T: …» — другие активные режимы, у которых после T стало хуже (P ≥ 0.95 при 15+ сессиях с каждой стороны);
- изменения в матрице переходов по разобранным сессиям до и после T, только те, что за пределами шума.

Правило вердикта разобрано в разделе о цифрах.

> **Важно:** «после» растёт только если по новым сессиям есть вердикты. Код-проверки активных режимов прогоняются при каждом импорте. Вердикты судьи появляются только в пакетах, по кнопке **Run Judge over the Pool…** (а она судит только разобранные сессии) и при валидации с судьёй. Если режим судит судья, гоняйте пакеты после T.

### Exemplars

Примеры — 2–3 цитаты (максимум 3), которые показывают режим. Они идут в каждый вызов сопоставления как «Example: …», а примеры из train-набора идут судье как образцы. Пример из сессии, которую адресату этого вызова слать нельзя, в вызов не идёт; у остальных их источники проверяются вместе с источником самой сессии. Хранятся в `modes/exemplars/<mode-id>.json`, каждое добавление и удаление — коммит.

- **Add from the Pool…** — окно поиска по всем принятым заметкам пула (сначала заметки этого режима). **Add** у заметки добавляет её цитату. Серая у сессий из любого тестового набора. Сама кнопка **Add from the Pool…** серая, когда примеров уже 3.
- **Remove** (кружок с минусом) у примера — удаляет его.
- Сессия из тестового набора никогда не может быть примером: примеры попадают в каждый вызов сопоставления, и тест «протёк» бы через них.

### Seen in N notes

Последний блок: заметки, сейчас отнесённые к режиму (первые 20, **Show all N** — все). У каждой сессия, шаг, описание и цитата.

- **Show Session Notes** — окно со всеми заметками этой сессии, её маршрутами и сигналами, с кнопками **Route Again…** и **Show Review Run** (см. «Окно заметок сессии» в разделе о Lab). Работает и для сессий пакетов.
- **Make Exemplar** — сделать цитату заметки примером. Нет, если примеров уже 3 или этот шаг уже пример. Серая для тестовых сессий.
- **Accept**, **Reject**, **Move to…** под заметкой — те же решения о маршруте, что на вкладке Review, но для любого маршрута, который привёл заметку сюда, в том числе уверенного. **Accept** есть, только пока маршрут модели не рассмотрен; он идёт в route acceptance. **Reject** без переноса оставляет заметку без маршрута; **Move to…** → режим, **None Fits** или **Unclear** переносят её.

## Вкладка Review
<!-- section: review -->

Здесь только то, что ждёт вашего решения. Число в названии вкладки — сколько дел в очереди (его нет, когда очередь пуста). После каждого пакета AKit не просит вас смотреть всё подряд: только кандидатов, сомнительные маршруты, сложные случаи, несколько случайных заметок и подозрительно широкие семена.

### Route acceptance

Вверху: «Route acceptance: k of n accepted». Это единственная метрика сопоставления: доля маршрутов, которые вы проверили и приняли. Считаются маршруты, поставленные моделью (сопоставление, кластеризация, ретро), по которым вы вынесли решение.

### Cluster Unmatched Notes… (N)

Кнопка справа. N — число принятых заметок пула с маршрутом «ничего не подходит» (заметки совсем без маршрута не входят). Открывает окно отправки:

- один вызов над этими заметками (описание и цитата каждой), плюс список текущих режимов («не повторять») и отклонённых («не предлагать»);
- модель возвращает группы: имя, вид, определение, include и exclude, список заметок;
- каждая группа становится режимом-кандидатом (коммит «Add mode …»), её заметки получают маршрут к нему;
- кандидат ждёт вас здесь же. Он также станет режимом сам, когда следующая независимая сессия получит к нему маршрут (сопоставлением, ретро или вами).

Заметки сессий, которые выбранному адресату слать нельзя, в вызов не идут, а итог в зелёной полосе добавляет «N of M notes left out: …» с причиной. Вызов не делается, только если нельзя слать ни одну заметку. Так же ведут себя **Retro-match…**, **First Modes…**, **Find Similar Cases…** и **Cluster All Notes Again…**.

Пакет делает то же самое автоматически в конце, но только над заметками своих сессий. Кнопка берёт весь пул. Нажимайте её после поштучных разборов, когда накопились заметки без режима.

### Candidate modes

Карточки кандидатов: имя, вид, «seen in k notes», определение. Кнопки:

- **Confirm** — сделать режимом, как на странице режима: код-проверка (если есть) сразу запускается, а над очередью появляется зелёная плашка со следующими шагами (**Run Check**, **Retro-match the Note Pool…**). Крестик справа её закрывает.
- **Rename…**, **Merge into…**, **Reject…** — как на странице режима.

> **Совет:** если два кандидата про одно и то же, слейте менее удачный в более удачный. Если кандидат слишком общий, лучше отклонить его с причиной «слишком широкий», чем подтвердить.

### Low-confidence routes

Заметки, для которых сопоставление (или ретро) не было уверено (меньше 0.6), и ещё не рассмотренные. Карточка: сессия, шаг, описание, цитата, куда модель отнесла заметку, уверенность и её объяснение.

- **Accept** — маршрут принят. Заметка начинает считаться в «seen in k notes» этого режима. Это плюс к route acceptance.
- **Reject** — маршрут отклонён. Минус к route acceptance. Если у заметки нет другого живого маршрута, она остаётся вообще без маршрута: не считается ни в одном режиме и не идёт в кластеризацию. Чтобы отправить её в кластеризацию, используйте **Move to…** → **None Fits**.
- **Accept** на маршруте ретро «also fits» переносит заметку в этот режим, из прежнего она уходит.
- **Move to…** → режим — старый маршрут отклоняется, а заметка получает ваш маршрут к выбранному режиму.
- **Move to…** → **None Fits** — отклонить и явно записать «ничего не подходит».
- **Move to…** → **Unclear** — то же, плюс заметка попадает в корзину Unclear (ниже).

После любого решения AKit проверяет кандидатов: если ваш перенос дал кандидату вторую независимую сессию, кандидат становится режимом. Все решения пишутся в маршруты заметок сессии (`notes/<session-key>.json`).

### Tough calls

Пограничные вердикты проверок текущих режимов: пока человек не решил, такой вердикт не входит в TPR и TNR. Блок читает те вердикты, что идут в отчёты: судьи, если он включён, иначе код-проверки. Сложные случаи на деле ставят только судьи (`checks/<mode-id>@judge.json`): код-проверки этот флаг не ставят. Карточка: режим, сессия и «The check says present at #n: …». Кнопки **Present** и **Not Present** записывают ваше решение в `labels/book.json`, и оно становится меткой для проверки. Пока сложные случаи не решены, валидация пишет «N tough calls left out».

### Spot checks

До 8 случайных принятых заметок модели из последнего пакета (меньше, если столько нет). Вопрос: это настоящая проблема? **Agree** или **Disagree** записывают ответ в `labels/book.json`, и заметка уходит из очереди. Если сессию потом разбирают снова, ответ переносится на ту же заметку нового разбора (тот же шаг и та же цитата), а ответ о заметке, которой больше нет, удаляется. Очередь читает только самый новый пакет: как только вы поставите следующий пакет, неотвеченные выборочные проверки прошлого исчезнут.

Ответы дают плитку **Spot checks** в шапке отчёта пакета на вкладке Reports: точность заметок модели — доля проверенных заметок этого пакета, с которыми вы согласились, «x% k/n». Пока ответов нет, там «no spot checks yet». Подсказка у заголовка блока говорит то же. Точность по подтверждённым парам на вкладке Bootstrap — отдельная цифра.

### Seeds that may be umbrellas

Семя, которому достаётся больше 30% всех отнесённых к режимам заметок (при 10+ заметках), возможно, слишком широкое («зонтик»). Кнопки **Edit…** (сузить критерии) и **Split…** (разделить).

### Unclear

Заметки, которые вы не смогли отнести ни к одному режиму (через **Move to…** → **Unclear**). Они хранятся в `labels/unclear.json`, потому что именно из них потом рождаются новые режимы. **Remove** только удаляет запись из корзины: маршрут заметки остаётся «ничего не подходит», и перенести её в режим из приложения в текущей версии нельзя.

Заметки стартового набора, которым вы в сопоставлении выбрали **Unclear**, сюда не попадают: они хранятся в разметке стартового набора.

## Вкладка Bootstrap
<!-- section: bootstrap -->

Стартовый набор: ваши собственные заметки на 30+ сессиях, написанные до того, как вы увидите заметки модели. Слева — список зарезервированных сессий и кнопки, справа — разметка выбранной сессии или обзор **Metrics and Mapping**.

### Зачем вы размечаете первым

Проверка заметок модели «на глаз» показывает только точность: не выдумала ли модель проблему. Но главный риск — полнота: что модель пропустила. Это видно только тому, кто сам прочитал транскрипт. Если вы сначала прочитаете заметки модели, вы начнёте искать то же, что нашла она, и пропустите то же, что пропустила она. Поэтому разметка слепая, а сессии резервируются.

### Сводка слева

- «k of n labeled» — сколько закончено из зарезервированных.
- «At least 30 are needed.»
- «Since the list of modes last changed: k (stop after 20)» — сколько размеченных сессий закончено после последнего изменения списка режимов (добавление режима, переименование, правка, слияние, разделение, отклонение, восстановление, подтверждение, активация семени). Зелёный цвет при 20+: можно останавливать стартовую разметку. Изменения фиксов, примеров и области не считаются. Кандидат кластеризации тоже не считается: список меняется, только когда кандидата подтвердят (вы или второй независимый случай).

У каждой сессии плашка: `to label` (не начата), `draft` (есть черновик), `labeled` (закончена).

### Pick Sessions…

Окно со счётчиком **Sessions** (по умолчанию 30, от 1 до 100) и кнопкой **Reserve**. AKit берёт из индекса сессии с 5+ запросами, кроме уже зарезервированных, уже разобранных моделью (их заметки вы могли видеть) и лабораторных. Группирует по «проект × слой» (харнесс | семейство модели | сильнейший сигнал) и берёт по одной случайной сессии из самых крупных групп (половина нужного числа), остальные — случайно.

Выбранные сразу записываются в `labels/reservations.json`. С этой минуты:

- поштучный разбор такой сессии будет отклонён при запуске («This session is reserved for bootstrap labeling; review it after you have labeled it»), пока вы её не разметите;
- пакеты её не выберут никогда, даже после разметки.

Окно говорит то же самое: выбранные сессии не берутся в поштучные разборы до разметки и не берутся в пакеты вообще.

Ничего не отправляется. Можно нажимать повторно, чтобы добавить ещё сессий.

> **Почему так:** зарезервированные сессии навсегда исключены из выборок пакетов. Иначе одна и та же сессия была бы и эталоном для измерения модели, и частью выборки, частоты по которой меряются.

### Разметка сессии

Слева транскрипт: шаги с номерами `#n` (та же нумерация, что видит модель), реплики пользователя выделены, вызовы и результаты инструментов свёрнуты в строки (раскрываются), «мышление» скрыто. Текст замаскирован так же, как его увидела бы модель (секреты, ваши шаблоны хостов и e-mail).

Справа форма. Вверху напоминание: «The model's notes on this session stay hidden until you finish».

- Нажмите номер шага (например, **#42**): шаг подсветится, в поле **Step #** подставится номер, в поле цитаты — первая строка шага, а в блоке **New note** появится окошко с текстом шага (до 20 000 символов). Выделите в нём мышью нужный кусок — он станет цитатой.
- **What went wrong** — что пошло не так, своими словами.
- **Quote from the step** — цитата (можно поправить руками).
- **Add Note** — добавить заметку в список **Your notes**. Кнопка серая, пока нет описания, номера шага и цитаты.
- **Clear** (появляется, когда в **What went wrong** или в цитате что-то есть) — очистить оба поля.
- Корзина у заметки удаляет её (только в черновике).
- **Outcome**: Achieved, Partly, Not achieved, Unclear — достигла ли сессия цели пользователя, по тому, что видел пользователь.
- **Decided about step** — шаг ошибки, которая решила исход. **Visible about step** — первый момент, когда проблема стала видна, если позже. Кнопки **Use #n** подставляют выбранный шаг. Оба шага приблизительные: «примерно здесь» достаточно.

Слой вины и «корень или симптом» у человека не спрашиваются.

### Save Draft и Finish

**Save Draft** сохраняет черновик в `labels/bootstrap/<session>.json`. Сессия остаётся зарезервированной.

**Finish…** (нужен исход) сохраняет разметку как законченную и снимает «слепоту»: теперь модель может разобрать эту сессию. Заметкам даются id `h1`, `h2`…, фаза каждой вычисляется кодом по шагу. Id не меняются: сохранённая заметка держит свой id при любом следующем сохранении, новая получает следующий ещё не использованный номер (номер удалённой заметки больше никому не даётся).

- Если в **What went wrong** или в цитате остался недописанный текст, **Finish…** не продолжает и пишет «A note is still being written: Add Note, or Clear it, before you finish». Так заметка не потеряется молча.
- Иначе появляется окно «Finish labeling this session?» с объяснением, что будет дальше. **Finish** в нём заканчивает разметку, **Cancel** — нет. Клавиша Return кнопку **Finish…** не нажимает.

После окончания сессия открывается в режиме просмотра. Чтобы что-то поправить, нажмите там **Reopen for Editing…** (см. ниже).

### Queue Model Notes…

Доступна, когда хотя бы одна сессия размечена. Окно: **Harness**, **Model**, **Effort**, **Open in** (**Automatic**, Orca, herdr или Background — где откроется вкладка пакета, как `--env` у `akit analysis bootstrap notes`), оценка стоимости, кнопка **Queue N Sessions**. Оценка зависит только от модели: прошлые записанные стоимости по усилию не разделены, поэтому **Effort** её не меняет. Ставит в Lab один пакет «Bootstrap: model notes on N labeled sessions» по всем законченным сессиям (не по выборке, вероятность включения 1). Для каждой: заметки, проверка, сопоставление, судьи активных режимов; в конце кластеризация и запись совпадений семян (как у обычного пакета). Отчёт по нему тоже появится на **Reports** с пометкой «bootstrap».

Пока такой пакет идёт, законченная сессия, до которой он ещё не дошёл, по-прежнему показывает «No model has reviewed this session yet» и обе кнопки: не ставьте разбор второй раз.

Повторный запуск снова включает все размеченные сессии. Те, что уже разобраны той же моделью, не переписываются (тот же ключ готовности), но сопоставление пройдёт заново, если список режимов изменился.

> **Совет:** используйте ту же модель, что будет у пакетов. Метрики стартового набора и матрица в отчётах привязаны к версии заметок.

### Законченная сессия: The model's review

У законченной сессии справа: ваши заметки, исход, шаги и кнопка **Reopen for Editing…**, ниже блок **The model's review**.

**Reopen for Editing…** возвращает разметку в черновик (дата окончания стирается): сессия снова открывается в форме разметки, её можно поправить и снова нажать **Finish…**. Сначала окно «Reopen this label for editing?» предупреждает: пока разметка не закончена заново, она не входит в метрики стартового набора и ни одна модель не может разбирать сессию; а если вы уже видели заметки модели по этой сессии, правка больше не слепая и полнота и точность, измеренные по вашей разметке, сдвигаются в сторону модели. Кнопка серая, пока разбор этой сессии стоит в очереди или идёт. Заметки модели и пары при этом не удаляются. Если в черновике вы удалите свою заметку (кнопка с корзиной), при сохранении вместе с ней исчезают её сопоставление с режимом (**Metrics and Mapping**) и её пары; остальные заметки сохраняют свои id, сопоставления и пары. Отметки **A real problem** у заметок модели остаются.

Блок **The model's review**:

- если модель ещё не разбирала: **Review with Model…** (окно с моделью, **Queue and Start**: обычный разбор одной сессии в Lab, как с экрана Sessions; работает и для сессий Pi) или **Queue Model Notes…** (один пакет по всем размеченным);
- если поштучный разбор стоит в очереди или идёт: «A review is queued in the Lab» или «A review is running in the Lab» и **Show in Lab**;
- если разбор есть: «N notes, k accepted by the verifier · версия заметок» и кнопка **Propose Pairs…** (или **Propose Again…**).

### Propose Pairs… и пары

**Propose Pairs…** — окно отправки. Модели уходят ваши заметки и все заметки модели по этой сессии (описания, шаги, цитаты; отклонённые проверяющим тоже, потому что меряется и сам проверяющий). Модель предлагает пары «ваша ↔ модели» про одну и ту же проблему. Результат в `labels/pairs/<session>.json`.

Ниже появляется редактор **Pairs**:

- слева ваши заметки, у каждой список **Same problem as** — выберите заметку модели или **None**; одна заметка модели может быть только в одной паре;
- справа заметки модели, у каждой переключатель **A real problem** — отметьте те, с которыми вы согласны как с настоящей проблемой; у заметок из предложенных пар он сразу включён, и при выборе пары включается сам;
- **Confirm** (или **Save Changes**) сохраняет подтверждённые пары и согласия. Только подтверждённые пары идут в метрики.

**Propose Again…** запрашивает пары заново. Подтверждённые вами пары и отметки **A real problem** остаются (для той же версии заметок и тех же заметок), так что сессия из метрик не выпадает. Новые предложения модели видны в редакторе; чтобы они вошли в метрики, снова нажмите **Confirm** (**Save Changes**).

Пары привязаны к тому разбору, на котором вы их сделали: у каждого нового разбора модель нумерует свои заметки заново (`n1`, `n2`… могут достаться другим заметкам). Поэтому, когда сессию разбирают снова (например, она выросла), AKit переносит пары и отметки **A real problem** на те же заметки нового разбора: заметка та же, если совпадают шаг и цитата. Пары с заметками, которых в новом разборе нет, удаляются. Пары, сделанные на ещё более раннем разборе, в метрики не идут.

### Metrics and Mapping: Agreement with the model

Первая строка списка слева открывает обзор. Таблица по каждой версии заметок (харнесс · модель · версия промпта), только по сессиям с подтверждёнными парами:

- **Sessions** — сколько таких сессий.
- **Recall** — доля ваших заметок, у которых есть подтверждённая пара с заметкой модели, принятой проверяющим. «Сколько ваших проблем нашла модель и оставил проверяющий». Так полнота меряется по тем же принятым заметкам, что и точность, пул и отчёты.
- **Before verifier** — то же до проверяющего: пары с любой заметкой модели, в том числе отклонённой. Разница с **Recall** — сколько полноты стоили отказы проверяющего.
- **Precision** — доля принятых проверяющим заметок модели, которые вы отметили как настоящие.
- **Phase** — доля сессий, где решающий шаг ваш и модели попал в одну фазу работы (фаза по коду).
- **±3 steps** — доля, где решающие шаги отличаются не больше чем на 3.
- **Outcome** — доля совпавших исходов.

В скобках «k/n». Фаза и шаги считаются только по сессиям, где оба указали решающий шаг.

> **Почему так:** матрица переходов в отчётах показывается, только если совпадение фаз для этой версии заметок не ниже 70%. Если модель плохо находит решающий шаг, матрица по её шагам врала бы.

### Your notes → modes и First Modes…

**First Modes…** — окно отправки. Один вызов кластеризации над вашими заметками и заметками модели по всем законченным сессиям (плюс текущие режимы «не повторять» и отклонённые «не предлагать»). Каждая группа становится кандидатом. Подтверждайте их на вкладке **Review** или **Modes**. Семена уже есть в списке.

Под кнопкой карточки законченных сессий с вашими заметками. У каждой заметки список: **Not mapped**, текущие режимы (включая кандидатов и неактивные семена), **Unclear**. Выбор сохраняется сразу в `labels/book.json`.

Это сопоставление — единственный путь, которым ваши заметки становятся метками для проверок:

- сессия положительна для режима, если хоть одна ваша заметка в ней сопоставлена с этим режимом;
- законченная сессия отрицательна для всех остальных режимов.

> **Важно:** несопоставленная заметка о настоящей проблеме превращает сессию в ложный «нет» для соответствующего режима. Сопоставьте всё, что можете. Если не можете — **Unclear**.

### Similar cases и Finds

Для каждого режима, с которым сопоставлены ваши заметки, строка «имя · N notes of yours» и кнопка **Find Similar Cases…** (окно отправки). Модели уходят ваши заметки этого режима и заметки всех остальных разобранных сессий (кроме размеченных вами) пачками по 80. Заметки сессий, которые этому адресату слать нельзя, не уходят, и итог говорит, сколько их осталось в стороне. Модель перечисляет похожие. Каждая находка ждёт вас в блоке **Finds**:

- **Accept** — положительная метка: в этой сессии режим есть.
- **Reject** — отрицательная метка.

Это дешёвый способ набрать метки для валидации судьи. Находки склонны к лёгким случаям, поэтому в тестовом наборе должны оставаться и метки стартового набора.

### Правило остановки и повтор

Останавливайте стартовую разметку, когда 20 размеченных подряд сессий не изменили список режимов (счётчик стал зелёным). Если вы поменяли модель заметок или промпт, разметьте 10–15 новых сессий и повторите пары: полнота меряется для каждой версии отдельно.

## Вкладка Reports
<!-- section: reports -->

Отчёт по одному пакету. Сверху два списка: **Batch** (какой пакет показать, по умолчанию самый новый) и **Compare with** (второй пакет для сравнения или **Nothing**). Название пакета: дата · проект (или «all projects», или «bootstrap») · сделано/всего.

Отчёт строится заново при каждом открытии: AKit читает транскрипты сессий пакета, чтобы вычислить фазы. На большом пакете это занимает несколько секунд. Ничего не отправляется.

### Шапка

Плитки переносятся на новую строку, если окно узкое. Рядом с процентом мелко «k/n» — из чего он посчитан.

- **Coverage** — сколько сессий пакета дошли до конца из всех. Под числом «sessions done» и, если есть, «N still running» (пакет ещё идёт), «N waiting, paused» (пакет на паузе), «N failed» (сессии с ошибкой: **Retry Errors** в Lab), «N too long for a digest» (такие сессии навсегда вне частот: самые длинные сессии в них не попадают) и «N left out before sampling» (сессии фильтра, которые автоматический рецензент не может получить по политике отправки; они не попали в выборку).
- **Notes recall** — полнота из стартового набора для версии заметок этого пакета, после проверяющего, и «k/n»: сколько ваших проблем найдено из скольких. Прочерк, если для этой версии нет подтверждённых пар.
- **Verifier rejected** — доля заметок модели в этом пакете, отклонённых проверяющим, и «k/n».
- **Spot checks** — точность по вашим ответам на выборочные проверки заметок этого пакета (вкладка Review), «k/n» — сколько вы подтвердили из скольких. «no spot checks yet», пока ответов нет.
- **Routes accepted · whole pool** — «k/n» маршрутов, которые вы приняли. Это общая цифра по всему пулу и всем пакетам, не только по этому, о чём и говорит подпись.

### Mode frequencies

Таблица по каждому активному режиму. Частоты только из проверок, по сессиям этого пакета, с весами выборки. Сопоставление здесь не участвует. Режим одного проекта (**Scope…**) считается только по сессиям этого проекта, а если их в пакете нет, в таблице его нет.

- **Mode** — имя. Оранжевая пометка «As frequent when the goal was reached: maybe not worth fixing» — режим одинаково част в успешных и неуспешных сессиях (разница меньше 5 пунктов).
- **Share (95% interval)** — точка на шкале с усами интервала и число. Для механической проверки это взвешенная доля, для провалидированной — поправленная на ошибки проверки. Подсказка при наведении объясняет, что именно.
- **Plain** — простая доля без весов, в процентах («k of n sessions» — в подсказке при наведении).
- **Goal reached / not** — взвешенная доля среди сессий с исходом «Achieved» и среди «Partly» и «Not achieved». «Unclear» не входит.
- **Check** — плашка доверия: `exact`, `validated`, `provisional`, `not validated`, и под ней «checked c/N»: у скольких законченных сессий пакета есть вердикт проверки из скольких, по которым режим считается.

Если проверка не механическая и не провалидирована, вместо трёх колонок «Seen in N notes» — сколько принятых заметок этого пакета отнесено к режиму. Если проверка «provisional» (20+ тестовых меток на класс, но граница не пройдена), ниже оранжевым «Provisional check: k of n (x%) — not a frequency».

Прочерк в **Share** у режима с точной или провалидированной проверкой значит, что у неё ещё нет вердиктов по сессиям пакета («checked 0/N»), и под прочерком сказано почему: код-проверки бегут после каждого импорта и в конце пакета (пока пакет идёт, их ещё не было), судья — по каждой сессии, когда пакет её разбирает.

«Below detection threshold» вместо числа: наблюдаемая доля не выше доли ложных срабатываний проверки (1 − TNR). Проверка не может отличить такую долю от нуля.

Все полоски на одной шкале (до ближайших 10% над самым большим интервалом).

### Saturation

- «x% of the notes matched no mode · new modes: …» — доля заметок пакета без режима и новые режимы. Новыми считаются найденные в заметках режимы, подтверждённые с момента создания пакета (по всему списку).
- Таблица по проектам: **Sessions**, **Unmatched**, **New modes**. Здесь «New modes» — сколько кандидатов, созданных кластеризацией этого пакета, получили заметки из сессий проекта. Это другое определение, чем в строке выше.
- «Both near zero for several runs in a row: the list of modes is saturated».

Оранжевая плашка с кнопкой **Cluster All Notes Again…** появляется, если больше 15% заметок без режима или если это каждый пятый пакет. Кнопка открывает окно отправки: все заметки пула кластеризуются заново, без списка режимов. Результат показывается блоком «Clustered from scratch: N groups (not saved)» и нигде не сохраняется. Группа, заметки которой сейчас разбросаны по нескольким режимам, помечена «Spans …: an umbrella, or modes to merge». **Dismiss** убирает блок.

> **Почему так:** пересборка с нуля проверяет, не навязал ли первый список режимов свою структуру. Если с нуля получается другое деление, стоит пересмотреть список. Но решать вам, поэтому ничего не сохраняется.

### Transition matrix

Матрица отвечает «на каком переходе ломается»: строка — фаза шага прямо перед действием решающего шага, колонка — фаза решающего шага. Если решающий шаг — результат инструмента, строка — фаза шага перед вызовом этого инструмента, а не сам вызов: иначе каждый упавший тест стоял бы в ячейке Verify → Verify. Фазы: Understand, Explore, Plan, Edit, Verify, Report. Плюс колонка **No failures**: сессии без принятых заметок (их всех кладут в строку Report). Ячейка показывает число сессий и долю, цвет следует доле. Клик по ячейке открывает список её сессий: исход, принятые заметки (решающая первой) с цитатами и кнопка **Show Session Notes** — окно со всеми заметками сессии (см. «Окно заметок сессии» в разделе о Lab).

Переключатель **Share of the batch** / **Share of the row**: доля от всего пакета («где горячо») или от строки («куда агент срывается после этой фазы»).

Матрица скрыта с объяснением, если:

- для версии заметок пакета нет замеров стартового набора («label and pair bootstrap sessions first»);
- совпадение фаз в стартовом наборе ниже 70%;
- пары подтверждены, но ни в одной сессии решающий шаг не указали и вы, и модель: совпадение фаз посчитать не из чего (сообщение то же, что в первом случае).

Если в пакетах этого же фильтра проекта меньше 50 законченных сессий, вместо матрицы показывается воронка **Deviations per phase**: сколько решающих шагов пришлось на каждую фазу.

Сессии с принятыми заметками, но без решающего шага, в матрицу не входят: «N sessions with failures but no decisive step are left out».

### Сравнение двух пакетов

Если выбран **Compare with**, появляется переключатель:

- **Side by side** — две матрицы на одной цветовой шкале, с N каждой;
- **Difference** — одна матрица изменений долей: красный — хуже, зелёный — лучше (в колонке No failures рост — хорошо), серый — в пределах шума (p Фишера ≥ 0.05), бледные ячейки — меньше 3 сессий с обеих сторон.

Для воронки — две воронки рядом. Таблицы частот и насыщения сравнением не затрагиваются.

## Вкладка Evals
<!-- section: evals -->

Контрольные задачи отвечают на вопрос «помог ли фикс» на фиксированных задачах, где состав задач не может сдвинуть цифру. Реальные сессии отвечают «что ломается и как часто». Слева наборы слоёв (**Layer Sets**, если они есть) и список задач, справа выбранный набор или выбранные задачи и сравнение.

### Что такое контрольная задача

Промпт, коммит репозитория, с которого агент начинает, и оракул (кто решает, прошла ли ячейка). Хранится в `~/.akit/lab/evals/tasks/<id>.json`. Создание задачи читает только git и индекс, ничего не отправляет.

Оракул бывает трёх видов:

- **Test command** — команда тестов проекта в клоне через `/bin/sh`, код выхода 0 = прошла. Можно указать reference — коммит, где тесты зелёные (обычно тот, что позже исправил проблему).
- **Mode's code check** — код-проверка режима на транскрипте ячейки. Ячейка проходит, если режима нет (у успешного режима — если есть). Доступны только пять режимов с код-проверками.
- **Hidden tests** (`hidden tests of a1b2c3d`) — только у задачи из коммита (**From Commit…**): тесты самого коммита. После агента их файлы копируются в клон; тесты, которые до коммита падали (fail-to-pass), должны пройти, остальные (pass-to-pass) — не сломаться. Как в replay из Lab, пока только для Swift-пакетов.

Режимы 2 и 3 (нарушенное ограничение, неверно понятый запрос) одной репликой не воспроизвести: им нужен протест пользователя. Их фиксы оцениваются только по реальной работе.

### From Session…

Окно «New Control Task from a Session». Список разобранных сессий и сессий-примеров (примеры первыми, с пометкой «exemplar of …»), поиск. Выберите сессию, при желании **Mode**, оракул, команду и reference, и при желании **Add to layer set** (**None** или слой мозга: задача сразу попадёт в его набор). **Save Task**.

Промпт — первая реплика пользователя дословно. Базовый коммит — HEAD, записанный хуком захвата в начале сессии. Репозиторий — тот, в папке которого шла сессия.

Сессия, у которой HEAD не записан (хук тогда не стоял), задачей не станет: окно покажет ошибку с советом написать воспроизведение.

То же окно открывается с экрана **Sessions**: кнопка со слоями **Add to Layer Set…** в шапке сессии Claude Code или Pi (подсказка «Make a control task from this session's first turn and add it to a brain layer's set (Error Analysis → Evals)»). Эта сессия уже выбрана в списке, а в **Add to layer set** стоит первый слой мозга. Кнопки нет, если в мозге нет слоёв, кроме core.

### Reproduction…

Окно «New Reproduction»: **Repository** (git-проекты или **Other…**), **Base commit** (sha или ссылка, например `HEAD~3`), **Prompt** — простейший запрос, вызывающий режим, затем режим, оракул и **Add to layer set**. **Save Task**.

### From Commit…

Окно «New Control Task from a Commit»: агент переделывает коммит, начиная с его родителя, а оракул — скрытые тесты самого коммита (**Hidden tests**). Поля: **Repository** (git-проекты или **Other…**), **Commit** (хеш) и **Add to layer set**. Ниже список недавних коммитов, которые меняют Swift-тесты; клик по коммиту ставит его хеш в **Commit**, пометка `checked` значит, что коммит уже проверен. **Check and Save** сначала проверяет коммит как задачу replay (тесты на родителе и на самом коммите: две локальные сборки, несколько минут, токены не тратятся), затем сохраняет задачу. Строка под списком показывает ход проверки. **Cancel** во время проверки останавливает сборки, и ничего не сохраняется. Уже проверенный коммит сохраняется сразу. Если у коммита уже есть задача, окно отдаёт её («The commit is already control task …»), а не делает вторую.

Промпт — сообщение коммита без строк `Co-Authored-By` и подобных плюс фраза «Implement this in the repository. Build and tests must pass. Commit when done.». Reference — сам коммит: на нём тесты зелёные по построению, поэтому **Check Reference** у такой задачи нет. Коммит без тестовых файлов, без Swift-пакета или без теста, который падает до коммита и проходит после, задачей не станет: окно покажет причину.

> **Почему так:** тесты коммита — готовый оракул, который судит результат, а не поведение. Но нужен коммит, чьи тесты не требуют нового API, которого агент не угадает: лучше всего подходят исправления и раунды ревью.

### Карточка задачи, Check Reference, Add to Layer Set… и Remove…

Справа у выбранной задачи: заголовок, плашка reference (`green`, `red`, `not checked`, `no reference`; у задачи из коммита плашки нет), репозиторий и коммит, оракул, источник («From session …», «Reproduction» или «From commit …»), режим, reference, **In sets** (наборы слоёв, где есть задача), id и промпт.

- **Add to Layer Set…** — меню слоёв мозга (без core): задача добавляется в набор выбранного слоя, набор создаётся, если его не было. Слой, в чьём наборе задача уже есть, серый. Набор берёт задачи только одного репозитория: задачу другого репозитория он отклонит.
- **Check Reference** (только у тестового оракула с reference) — делает изолированный клон на коммите reference, запускает команду тестов (до 15 минут), пишет лог в `~/.akit/lab/evals/reference-<id>.log`, клон отправляет в Корзину, результат пишет в задачу. Ничего не отправляет моделям. Если тесты красные, ячейки этой задачи ставить нельзя.
- **Remove…** → **Move to Trash** — файл задачи уходит в Корзину. Её ячейки остаются запусками Lab.

> **Почему так:** если тесты не зелёные даже на правильном решении, оракул не отличит фикс от шума. Поэтому красная задача блокирует запуск.

### Наборы слоёв (Layer Sets)

Набор слоя — задачи, на которых оценивается слой мозга, и ответы на поля слоя, с которыми он рендерится. Файл `~/.akit/lab/evals/sets/<слой>.json`, только на этом Mac: в мозг из набора ничего не попадает. Набор появляется, когда в него добавлена первая задача (**Add to Layer Set…**, **Add to layer set** в окнах новых задач или `akit analysis control layer-set СЛОЙ add ЗАДАЧА`). В боковой панели раздел **Layer Sets** со строкой на каждый набор (слой и число задач). Выбранный набор показывает свою страницу:

- Заголовок — имя слоя и «Layer set», кнопки **Run Cells…** (оценка слоя на задачах набора: окно **Run Cells** сразу открыто на **A brain layer** с этим слоем и с отмеченными задачами набора) и **Delete Set…** → **Move to Trash** (файл набора уходит в Корзину, задачи и ячейки остаются).
- **Tasks (N)** — задачи набора с репозиторием, коммитом и оракулом, у каждой **Remove from Set** (задача уходит из набора, но не удаляется). Задача, чей файл удалён, помечена «…: missing (removed from the tasks; skipped)»: оценки её пропускают.
- **Answers** — единственное место, где меняются ответы набора: поля слоя и слоёв, которые он требует. Пустое поле или **Default (…)** значит «ответа в наборе нет»: тогда действует сохранённый ответ проекта, потом значение по умолчанию из `layer.yaml` («An empty answer leaves the field to the project's saved answer, then the layer's default.»). Поле списка — значения через запятую. **Save Answers** сохраняет изменения, **Revert** их отменяет.
- **Evals (N)** — оценки этого слоя, новые сверху (и из Brain → **Evaluate…**, и из **Run Cells…**). В меню **Eval** выберите оценку (дата, модель, усилие, «N tasks × повторы»); под ним её id, коммит мозга и запрещённые команды («the agent may not run: …»), а ниже — **Setups compared** только по ячейкам этой оценки, с её вердиктом.

#### Оценка слоя из Brain: Evaluate…

Обычный путь оценки слоя — Brain → слой → блок **Evals** → **Evaluate…** (на слое core этой кнопки нет). Кнопка есть, когда в наборе слоя есть задачи; если набора нет, там **Create Layer Set** (пустой набор сразу открывается здесь, на вкладке Evals), а **Show in Error Analysis** открывает страницу набора. В окне **Evaluate СЛОЙ**:

- **Eval**: «Continue the eval of …: n of N cells done» — продолжить последнюю оценку этого слоя с той же моделью, если слой рендерится в те же файлы (готовые ячейки не идут заново); **Set** (задачи, пропавшие, заблокированные, репозиторий), **Answers** (только чтение; **Edit in Set…** ведёт на страницу набора), **Setups**, id оценки, «Home overlap».
- **Agent**: Claude Code, **Model**, **Effort**, **Repeats**, **Read-only sanity cells on 3 tasks (must fail)**, **The agent may not run**, **Open in**, **Keep the clones**. В **The agent may not run** — команды через запятую, которые агенту запрещены во всех ячейках обеих настроек (у Claude Code это `--disallowedTools "Bash(команда:*)"`). Для репозитория самого AKit там по умолчанию `make snapshot, make run, make restart, make install, make install-cli, make screenshots, make open, open, swift run`: `CLAUDE.md` AKit просит делать снимок экрана после правки UI, а в ячейке это собрало бы, поставило или запустило dev-AKit с вашим настоящим `~/.akit`. Тот же список AKit сам даёт в этом репозитории каждой контрольной ячейке (и из **Run Cells…**) и каждому реплею. Пишите команды, а не правила: `Bash(make run:*)`, скобки и `*` AKit не примет. Запрет смотрит на начало команды, поэтому `make -C . snapshot`, `make OUT=x snapshot`, прямой запуск собранного `AKit.app` или `.build/…/akit` он не ловит (`swift build` и `swift test` разрешены, `swift run` — нет). Продолженная оценка сохраняет свой список; если он пустой в репозитории AKit, окно предупредит.
- Под формой: «N cells to run (k already done or queued)», стоимость «≈ $X (range $L–$H) from n recorded control cells of Claude Code · opus» (по записанной цене прошлых контрольных ячеек этой модели, если их нет — реплеев; диапазон — самая дешёвая и самая дорогая записанная ячейка, умноженные на число ячеек) и время «≈ … in the Lab queue (one cell at a time, from n recorded run durations)». Когда у обеих настроек уже есть записанная ячейка, цена считается по каждой настройке отдельно: «≈ $X (range $L–$H) from the recorded cells of each setup (Claude Code · opus): without СЛОЙ n × $a (k recorded), layer СЛОЙ n × $b (k recorded), read-only n × $a (0 recorded)». Слой добавляет текст в контекст, поэтому его ячейки обычно дороже; ячейки read-only без своих записей считаются по цене базы. Пока записана только одна настройка, цена берётся по всем контрольным ячейкам модели, с пометкой «(not per setup: the layer setup has no recorded cell yet)».
- **Queue N Cells…** спрашивает «Queue N cells for about $X (range $L–$H)?» и ставит ячейки только после **Queue**; если в очереди Lab ждут другие запуски, в вопросе есть «k other queued runs will start too». Перед постановкой AKit ещё раз считает ячейки и цену: если ячеек стало больше («The eval changed since the estimate …; check it again») или верхняя граница выросла, ничего не ставится — откройте окно заново. Потом проверяется лимит на месяц.
- Если записей стоимости нет («No estimate yet: no recorded control or replay cell of Claude Code · opus.»), **Queue N Cells…** серая. Тогда есть **Queue 2 Calibration Cells…** («Queue 2 calibration cells?» — «2 paid cells, one of each setup on the same task, to measure what each costs; the eval reuses them.»): по одной платной ячейке каждой настройки, «without СЛОЙ» и «layer СЛОЙ», на первой задаче и первом повторе. Так оценка видит цену обеих настроек, а первая пара результатов уже есть. Ячейки read-only в калибровку не входят. Если у одной настройки ячейка уже есть (например, оценка, начатая до этого изменения, с одной ячейкой базы), кнопка называется **Queue 1 Calibration Cell…** и ставит только недостающую ячейку той же задачи. На каждую настройку не больше одной калибровочной ячейки: пока они идут, новые поставить нельзя (кнопка серая, подпись «The calibration cells are queued or running: …»). Когда они закончатся, снова откройте **Evaluate…**: появится оценка по каждой настройке, переключатель **Continue** уже включён, и калибровочные ячейки войдут в ту же оценку.
- **Проверка настройки (setup check).** Каждая ячейка оценки слоя проверяется дважды, чтобы скилл или текст слоя не попал не в ту настройку. Первая проверка — до запуска агента, без обращения к модели: в клоне, в папках над ним и в `~/.claude` (`CLAUDE.md` и его импорты, `rules`, `skills`). У «without СЛОЙ» не должно быть ни скиллов слоя (по имени), ни его текста, ни его файлов. У «layer СЛОЙ» должны быть все скиллы рендера (ручные — с `disable-model-invocation: true`) и текст слоя в файле, который читает Claude Code; скиллов, которые слой выключил (`mode: off`) или которые выпали по ответам, быть не должно. Собственные файлы проекта из его коммита есть в обеих настройках и не считаются утечкой. Если проверка не прошла, агент не запускается, запуск Lab падает с сообщением «Setup check failed for … , so the agent didn't start and the cell doesn't count: <путь> holds the skill <имя>, which this setup must not have», и ячейка ни во что не идёт; денег она не стоит. Если скилл или текст слоя лежит в `~/.claude`, его увидели бы все ячейки базы: окно показывает предупреждение «The setup without СЛОЙ would see what it must not: …», и постановка отказывает, пока вы его не уберёте. Вторая проверка — после агента, по списку скиллов, который Claude Code показал модели (запись `skill_listing` в транскрипте): у базы там не должно быть скиллов слоя, у слоя должны быть все его не ручные скиллы. Если нет, у ячейки «setup check failed: …», и сравнение и вердикт её не считают, а пишут, сколько таких («n cells failed the setup check, left out»). Если в транскрипте нет списка, пишется «not checked», это не ошибка.

То же в терминале: `akit analysis control evaluate СЛОЙ --model opus` печатает план и оценку («Calibration: 2 calibration cells, …») и ничего не ставит; `--calibrate --yes` ставит калибровочные ячейки (и печатает их ожидаемую цену, если она известна); `--yes --max-cost USD` ставит остальные, если верхняя граница оценки не больше USD (без оценки или без `--max-cost` отказывает); `--continue [ID]` и `--new` выбирают оценку; `--deny КОМАНДЫ` и `--no-deny` меняют запрещённые команды.

Пока набор берёт задачи только одного репозитория: от репозитория зависят `project_name` и сохранённые ответы проекта. Рабочие копии (worktree) одного репозитория считаются одним репозиторием: имя проекта и его ответы берутся из основной папки. Задачу другого репозитория набор отклоняет («… a set takes the tasks of one repository for now …»).

### Run Cells…

Выделите одну или несколько задач (⌘-клик) и нажмите **Run Cells…**. Окно **Run Cells**:

- **Tasks** — галочки задач.
- **Setups**:
  - **Baseline: the task as is** — агент как есть;
  - **Variant: one difference from the baseline** — ровно одно отличие: **File and text** (файл `CLAUDE.md`, `AGENTS.md` или `.claude/skills/NAME/SKILL.md` и текст), **A mode's fix draft** (черновик фикса выбранного режима) или **A brain layer** (слой из мозга, см. ниже «Слой мозга как отличие»);
  - **Read-only sanity setup (must fail)** — агент только с инструментами чтения. Его ячейки обязаны провалиться: это проверка, что оракул работает.
- **Agent**: **Harness**, **Model**, **Effort** (у Pi вместо него **Thinking**), **Repeats** (по умолчанию 3 на задачу и настройку), **Open in**, **Keep the clones**.
- Строка стоимости: «Up to N cells; ≈ $X (range $L–$H) from k recorded control cells of …» и время в очереди Lab, или «Up to N cells; no estimate yet (…)» (оценка появляется после первой контрольной ячейки или реплея этой модели). Та же оценка, что в Brain → **Evaluate…**.

С **A brain layer** правило денег то же, что в Brain → **Evaluate…**: пока у модели нет записанной цены, кнопка серая, и окно отправляет в Brain → слой → **Evaluate…** за калибровочными ячейками (по одной на настройку); когда цена есть, кнопка называется **Queue N Cells…** и сначала спрашивает «Queue up to N cells for about $X (range $L–$H)?». В терминале `run --layer … --yes` так же требует оценку и `--max-cost USD`.

Любая постановка из **Run Cells** платная, поэтому окно сначала считает, сколько ячеек ещё нужно запустить, и оценивает их («N cells to run (k already done or queued); …»). **Queue N Cells…** открывает вопрос «Queue up to N cells for about $X (range $L–$H)?», а если цены ещё нет — «Queue N cells with no estimate yet?», и ставит ячейки только после **Queue**. Подсказка про выключенную базу говорит «Its cells are all done or queued, so it costs nothing», только если ячеек базы ставить уже не нужно. В терминале `run … --yes` без `--layer` показывает число ячеек и оценку; когда цена записана, нужен ещё `--max-cost USD`.

**Queue N Cells…** серая, если для Claude Code не заполнено **Model**, если среди задач есть красная, если выбран вариант без готового отличия или вариант без базы. Вариант сравнивается только с базой того же агента, поэтому без галочки **Baseline** окно просит её включить. Уже сделанные ячейки базы пропускаются, так что там, где база уже шла, это ничего не стоит. Черновик фикса со слоем Hook, Tool description или Environment даёт сообщение «This draft's layer (…) isn't a file in the repository, so it can't be tried here», и вариант ничего не ставит.

#### Слой мозга как отличие

**Difference** → **A brain layer** — это оценка слоя: помогает ли слой агенту на этих задачах. Переключатель **Baseline** исчезает: настроек всегда две, и окно строит их само.

- **Layer** — слой мозга. Слоя core в списке нет: это слой домашней папки, он и так есть в каждой ячейке.
- База — «without СЛОЙ»: только слои, которые слой требует (`requires`), или ничего, если он ничего не требует. Вариант — «layer СЛОЙ»: те же слои и сам слой. Так сравнение убирает ровно этот слой.
- Слой рендерится один раз, из коммита мозга, только для Claude Code. Поля берутся сначала из ответов набора слоя (**Answers** на странице набора), затем из сохранённых ответов проекта (если проект настроен через AKit), затем из значений по умолчанию в `layer.yaml`. Обязательное поле без значения — ошибка, ячеек не будет: ответьте на него в наборе слоя или для проекта в **Brain** → **Set Up Project…** (в командной строке значение задаёт ещё и `--answer ПОЛЕ=ЗНАЧЕНИЕ`, поверх ответа набора).
- Текст слоя для `AGENTS.md` дописывается в тот файл, который Claude Code уже читает в клоне: в собственный `CLAUDE.md` проекта (или в `AGENTS.md`, если `CLAUDE.md` его импортирует). Скиллы слоя ложатся в `.agents/skills`, рядом ссылка `.claude/skills`. Всё это спрятано от `git status`. Настоящий репозиторий и мозг не меняются.
- Под выбором слоя — подпись «Baseline: the layer's required layers alone; variant: them and the layer. … the layer's text is appended to the file Claude Code reads in the clone.», две строки настроек с хешами их наборов файлов («overlay … »), «N of M tasks can run · eval …», заблокированные задачи с причиной, по строке на каждый собственный файл проекта, куда попадёт текст слоя («N tasks: the layer's text is appended to the project's own CLAUDE.md; the project would get it only by accepting the suggestion.»; вместо `CLAUDE.md` может стоять `.claude/CLAUDE.md` или `AGENTS.md`), и предупреждения о скиллах слоя, которые у вас уже установлены («… is already installed in the home folder: the difference will look smaller than it is»). Пока слой рендерится, видно «Rendering the layer…».
- Задача блокируется, если в её коммите уже есть файл, который слой пишет целиком, своя папка `.claude/skills` (так же отказывает и Apply) или ссылка, ведущая из репозитория наружу. Ещё блокируется проект, где есть `AGENTS.md`, но нет ни `CLAUDE.md`, ни `.claude/CLAUDE.md` («The project has AGENTS.md but no CLAUDE.md; AKit can't yet tell what Claude Code reads there.»): пока не проверено, читает ли Claude Code такой `AGENTS.md` сам. Собственный скилл проекта с тем же именем побеждает: копия слоя пропускается.
- Каждую ячейку со слоем AKit проверяет до агента и после него, как в Brain → **Evaluate…** (см. там «Проверка настройки»): ячейка, где скилл или текст слоя попал не в ту настройку, не запускается или не идёт в сравнение.
- Слой отказывает целиком, если в мозге есть незакоммиченные изменения в его папке, в папках требуемых слоёв или их скиллах, если он сливает ключи в `.mcp.json` или `.claude/settings.json`, если задачи из разных репозиториев или если выбран Pi («Layer evals run Claude Code only for now.»).
- **Read-only sanity cells on 3 tasks (must fail)** — по одной ячейке только с инструментами чтения на первых трёх задачах, без слоя. Они ставятся сразу после первого повтора, чтобы сломанный оракул был виден рано.

Каждое нажатие **Queue N Cells** создаёт новую оценку (eval) со своим id: папка `~/.akit/lab/evals/layer-evals/<id>/` с манифестом и файлами слоя, затем ячейки. Ячейки одной оценки сравниваются только между собой, и готовые ячейки других оценок не переиспользуются. Продолжить оценку (те же задачи, настройки и число повторов, готовые ячейки пропускаются) пока можно только командой `akit analysis control run --layer СЛОЙ --eval ID`, без списка задач; другой список задач или другое `--repeats` она отклонит, и откажет, если слой с тех пор рендерится иначе. AKit ставит такие ячейки только через команду `akit`, которая знает слои; более старую попросит обновить.

> **Почему так:** база — это ваша настоящая домашняя папка, поэтому вопрос звучит «добавляет ли слой что-то к тому, что у меня уже есть». Обе стороны идут в одной очереди вперемешку и с одной домашней папкой. Если Claude Code за время оценки обновился, сравнение это покажет: «The cells mix Claude Code versions: …».

**Queue N Cells** ставит в Lab N = повторы × задачи × настройки ячеек, чередуя (сначала первый повтор всего, потом второй), чтобы недоделанное сравнение оставалось честным. Перед этим проверяется месячный лимит с оценкой. Ячейки, уже сделанные с тем же ключом (задача, настройка, коммит, номер повтора) без флагов, и стоящие в очереди пропускаются.

Каждая ячейка — полноценный запуск агента:

1. Проверка политики: код репозитория уходит агенту выбранного харнесса; для задачи из сессии ещё и источник той сессии должен быть разрешён. Промпт маскируется.
2. Свежий репозиторий только с историей базового коммита (не worktree, не клон с remote): позднее исправление в нём недостижимо.
3. Вариант дописывает текст в файл клона и прячет это от `git status`.
4. Агент работает под сторожем памяти: если его собственный `swift test` в клоне разрастается больше 2 ГБ, процесс тестов убивается. Затем оракул; у задачи из коммита это скрытые тесты: их файлы копируются в клон, пакет собирается, каждый тест идёт отдельным процессом (лог в `check.log` ячейки).
5. Охрана: число тестов не уменьшилось, тестовые файлы не изменились, агент не читал исходную сессию, историю сессий и настоящий репозиторий. Флаг ставит и заглядывание в Корзину (`~/.Trash`): туда уходят готовые клоны и папка проверки коммита. У задачи из коммита охрана не смотрит на файлы скрытых тестов (агент может дописать в них свои тесты, их всё равно заменят), зато флагом станет и хеш коммита в вызовах инструментов или их результатах, и чтение папки Lab (`~/.akit/lab`). Поэтому задачи из коммита пока идут только с Claude Code («Hidden-test tasks run Claude Code only for now.»). Нарушение — флаг: ячейка считается проваленной и заново не ставится.

   Как охрана читает вызовы инструментов:
   - Настоящий репозиторий — это и папка задачи, и основная папка репозитория. Если задача сделана в worktree, чтение основной копии (main checkout) тоже флаг. Путь в домашней папке узнаётся и в виде `~/…`, `$HOME/…`, `${HOME}/…`, но только как целая папка: `~/Projects/akit-other` не считается путём к `~/Projects/akit`.
   - Путь к репозиторию, Корзина, хеш коммита и id исходной сессии ищутся во всём вызове, вместе с текстом, который агент пишет в файл. Поэтому скрипт, который агент написал и потом запустил, тоже попадётся.
   - Папка Lab (`.akit/lab`) и история сессий (`.claude/projects`, `.pi/agent/sessions`) ищутся только в том, что вызов запрашивает: команда, путь, шаблон файлов. В исходниках AKit эти пути упоминаются, и правка исходников — не утечка. У `Grep` шаблон (`pattern`) — это поиск по тексту, а не путь, поэтому `Grep` по исходникам со словом `.akit/lab` не флаг, а `Glob` или `Grep` с путём в `~/.akit/lab` — флаг. Текст поручения субагенту, списка дел, плана и вопроса пользователю ничего не запрашивает, но путь к репозиторию, Корзина и хеш в нём считаются.
   - Вызовы субагентов Claude Code (их отдельные файлы `<сессия>/subagents/*.jsonl`) проверяются так же, как вызовы самой ячейки.
6. Стоимость пишется в журнал отправок (purpose `control`). Клон уходит в Корзину, если не стоит **Keep the clones**.

### Setups compared

Под карточками задач — таблица по настройкам (только законченные ячейки выбранных задач; бутстреп считается в фоне один раз на каждый новый набор законченных ячеек, и пока он идёт, на месте таблицы крутится индикатор):

- **Setup** — имя и агент, под ним «задача: прошло/всего».
- **pass@1** — шанс, что один запуск пройдёт: среднее долей по задачам. Интервал Wilson по всем ячейкам вместе.
- **pass^k** — доля задач, где прошли все k запусков; k — наименьшее число ячеек у задачи. Интервал — бутстреп по задачам.
- **Cells** — сколько ячеек, и сколько из них «flagged, counted as failed».

Ниже для каждого варианта плашка вердикта. Вариант сравнивается с базой того же агента (если её нет — с первой базой) и только на задачах, где ячейки есть у обеих настроек. Слой мозга («layer СЛОЙ») сравнивается только с «without СЛОЙ» своей же оценки и того же агента, никогда с обычной базой, и у него свой уровень вердикта (см. ниже «Вердикт слоя»). Если ячейки пары шли на разных версиях Claude Code, под плашкой «The cells mix Claude Code versions: …». Ячейки слоя, которые выполнила старая команда `akit` без слоя, в таблицу не входят: строка «N cells run by an older akit, left out: it ignored the layer. Install the app and akit together.» В плашке: `helped`, `helps (offline)` (только у слоя), `didn't show it helped`, `no conclusion`, среднее изменение «±N points per task», доля массы бутстрепа на улучшении и причина. Правило: 95%+ массы на улучшении, 3+ повтора каждой задачи с каждой стороны, 15+ ячеек с каждой стороны, и «не хуже в реальной работе»: проверка режима задач по сессиям индекса даёт не больше 50%, что доля отказов выросла после T фикса, при 15+ сессиях с вердиктом с каждой стороны. Правило зафиксировано до запуска, подпись под плашками повторяет его.

Сигнал реальной работы есть, только если выбранные задачи, у которых указан режим, указывают один и тот же, и его фикс применён (**Mark Applied…**). Без него вариант даже при 95%+ массы получает `no conclusion` с причиной: у режима нет применённого фикса или с какой-то стороны T меньше 15 сессий. Пока вы пробуете черновик фикса на задачах до применения, `helped` не бывает.

#### Вердикт слоя

Слой оценивают до того, как кто-то начнёт с ним работать, поэтому сигнала реальной работы у него нет и не нужно. У пары «layer СЛОЙ» против «without СЛОЙ» свой уровень: плашка `helps (offline)` (зелёная), если 95%+ массы бутстрепа на улучшении, 3+ повтора каждой задачи и 15+ ячеек с каждой стороны. Ниже порога — `didn't show it helped`, при малом числе ячеек или повторов — `no conclusion`. Если хоть одна ячейка «только чтение» этой же оценки прошла, пара остаётся `no conclusion` с причиной «A read-only agent passed ЗАДАЧА: its oracle can't tell work from no work». Фикс режима (вариант с текстом или черновиком) `helps (offline)` не получает никогда: его правило прежнее. Подпись под плашками: «… A brain layer is compared only with its own eval's required layers and has its own level, helps (offline): the same 95% without production data, unless a read-only cell of its eval passed. A fix never gets it.»

У пары слоя в строке плашки рядом с долей на улучшении стоит доля на ухудшении («… of the bootstrap mass on improvement, N% on worse»): доля повторов бутстрепа, где среднее изменение меньше нуля; повторы ровно с нулём не идут ни туда, ни туда.

Пока ячейки оценки стоят в очереди или идут, под плашкой «The eval's verdict waits for N cells still queued or running.». Когда открытых ячеек у оценки не осталось, под плашкой блок «Verdict of the eval (all its tasks), saved for the layer:» — четыре строки по всем задачам оценки (не только выделенным):

```
swiftui · Claude Code · opus · high · 5 tasks × 3 · eval 2026-10-08 · brain 53c89bb
success: 0% → 100%, helps (offline) (100% of the bootstrap mass on improvement, 0% on worse; needs 95%)
read-only sanity: 0 of 3 passed · Claude Code 2.1.290
home overlap: none · 5 tasks with the project's own CLAUDE.md or AGENTS.md (the project gets the layer's text only by accepting the suggestion) · $0.33
```

Первая строка — слой, агент, задачи × повторы, дата оценки и коммит мозга. Вторая — успех без слоя и со слоем и вердикт. Третья — проверка «только чтение», флаги, заблокированные задачи, ячейки старой `akit` и версии Claude Code (с пометкой «mixed versions», если их несколько). Четвёртая — пересечение со скиллами домашней папки, задачи с собственным `CLAUDE.md` или `AGENTS.md` проекта и записанная стоимость ячеек. Тот же вердикт AKit сохраняет как последний для этого агента (харнесс, модель, effort) в `~/.akit/lab/evals/verdicts/СЛОЙ.json`: только числа, без промптов и путей; в мозг ничего не попадает. Более старая оценка не заменяет вердикт более новой: тогда заголовок блока «Verdict of the eval (all its tasks); a newer eval's verdict is kept for the layer:». Оценка, где ни у одной задачи нет законченных ячеек обеих настроек (например, всё отменено), вердикта не даёт и сохранённый не трогает. Ячейка «только чтение» этой оценки считается и тогда, когда её задача не выделена. Если манифест оценки не читается, под плашкой причина (например, «The eval … was written by a newer AKit; install the app and akit together.»). Если файл не удалось записать, заголовок блока «Verdict of the eval (all its tasks), not saved:», а внизу «The layer's verdict couldn't be saved: …». В командной строке то же даёт `akit analysis control compare --eval ID` (`--json` для машинного вида).

> **Совет:** набор растёт до 20–30 задач раньше, чем число повторов. Три задачи по десять повторов говорят о трёх задачах, а не о фиксе.

<!-- section: lab -->

### Общее про Lab

Lab выполняет запуски по одному: остальные ждут в очереди. Запуск открывается во вкладке Orca, в herdr или в фоне (**Open in**). Экран читает папки запусков каждые две секунды. Общие кнопки на странице запуска:

- **Show in Orca** / **Show in herdr** — вывести вкладку запуска вперёд.
- **Cancel** — остановить идущий (вкладка остаётся) или убрать из очереди.
- **Start** (у любого запуска в очереди, который ещё не стартовал) — запустить следующий в очереди; нужна, если автозапуск остановился после ошибки.
- **Show in Finder** — папка запуска `~/.akit/lab/<run-id>`.
- **Remove…** → **Move to Trash** — папка запуска в Корзину. Заметки, пакетный файл и метки анализа остаются.

> **Важно:** AKit узнаёт свои лабораторные сессии (ячейки, повторы) по папкам запусков. Если удалить запуск ячейки, её сессия перестанет считаться лабораторной и может попасть в выборки и частоты. Не удаляйте ячейки, пока ими пользуетесь.

### Разбор одной сессии с заметками

Запускается с экрана Sessions (кнопка с колбой у сессии Claude Code), из **New Run…** → **Review a Session** (список только сессий Claude Code) или с вкладки Bootstrap (**Review with Model…**, там можно и сессии Pi).

Поле **How**: **One model call** — то, что нужно анализу; **Agent with file tools** — старый разбор агентом, без заметок.

Что делает разбор в режиме одного вызова:

1. Отказывается, если сессия зарезервирована под стартовую разметку и не размечена.
2. Проверяет аккаунт и политику, маскирует транскрипт, строит дайджест.
3. Заметки, проверка, сопоставление со всеми текущими режимами (тем же агентом). Если сопоставление не удалось, разбор не падает: заметки просто остаются без маршрутов.
4. Пишет `notes/<session-key>.json` (заменяя прежний разбор этой сессии), а для экрана Lab — абзац и советы.

На странице запуска (блок под заголовком), сначала итог, потом подробности:

- **Карточка итога**, цвет по исходу (зелёная — сделано, оранжевая — частично или есть серьёзная проблема, красная — не сделано, серая — неясно):
  - первая строка: «✅ Done», «🟡 Partly done», «❌ Not done» или «❔ Unclear whether done» и число принятых проблем по серьёзности: «🔴 1 high · 🟠 2 medium · ⚪ 1 low» (или «no problems found»);
  - заключение проверяющего в одно-два простых предложения: хороша ли была сессия, какая проблема стоила дороже всего и что одно стоит поменять. Пишется только по принятым заметкам. У разборов, сделанных до появления заключений, вместо него подсказка «No conclusion yet»: **Re-check with Another Model…** с той же моделью, тем же усилием и тем же языком разбора (Settings → Lab) возьмёт готовые заметки и заново запустит только проверку и сопоставление (два вызова вместо трёх). В окне заметок сессии, где этой кнопки нет, подсказка говорит, что заключение напишет следующий разбор;
  - размер разобранной сессии (только Claude Code): «⏱ 2 hr, 35 min · 164 calls · 515K fresh tokens · peak context 397K».
- **What to Change** — до трёх советов «👉 …» и что каждый улучшит. **Evidence (n1)** раскрывает доказательства из сессии и заметки, на которых совет стоит.
- **Problems by Type** — принятые заметки, сгруппированные по режимам анализа ошибок так же, как их считают страницы режимов на экране Error Analysis (подсказка у заголовка — определение режима). Метка «Type unconfirmed» у заметки — сопоставление было не уверено (ниже 0.6), а вы маршрут ещё не смотрели: примите или перенесите его на вкладке Review; страницы режимов такую заметку пока не считают. «No type yet» — заметки, которым ни один режим не подошёл или которые ещё не сопоставлялись; из таких кластеризация делает новые режимы. У заметки: id, шаг, фаза, серьёзность, слой вины, «symptom of …», описание и раскрывающаяся **Quote**. У заметок высокой серьёзности раскрывается «The verifier's case against it» — аргумент проверяющего против. Если принятых нет: «Checked, no failures» — такая сессия тоже считается в знаменателях.
- **Details: what happened, requirements, rejected notes** (свёрнуто):
  - строка «Notes by …; verified by …»;
  - **What Happened** — абзац о ходе сессии. Он пишется до проверки, поэтому может упоминать отклонённую заметку: верьте заключению в карточке;
  - **Requirements** — требования задачи, выписанные из реплик пользователя;
  - **Where It Went Off** — «Decided about step #n», «Visible about step #m», оба приблизительные;
  - **Rejected by the verifier (N)** — отклонённые, с причиной: «Rejected by code» (цитата не найдена в указанном шаге, или она короче 8 символов, или у цитаты с «…» все части короче 8 символов) или «Rejected by the verifier model».

Повторный разбор той же сессии той же моделью с теми же настройками и на неизменённом файле не вызывает модель заново: заметки и проверка берутся по ключу готовности.

> **Важно:** проверка, которая пишет заключение, — новая версия (3). Поэтому следующий разбор каждой уже разобранной сессии — в пакете, в **Queue Model Notes…** или поштучно — один раз заново вызовет проверку и сопоставление (платно, но без переписывания заметок: они берутся по ключу).

### Re-check with Another Model…

Кнопка у законченного разбора. Окно показывает, какой моделью сделан этот разбор, и даёт выбрать **Harness**, **Model**, **Effort**; кнопка **Queue and Start**. Ставит новый разбор той же сессии другой моделью: заметки, проверка и сопоставление с режимами (после него AKit, как всегда, проверяет кандидатов на повышение). Его заметки заменяют заметки этого разбора в пуле. Старый запуск сохраняет свой абзац и советы и показывает «A later review of this session replaced its notes» с кнопкой **Show Review**.

Используйте для трудных сессий, где нужен второй взгляд. Это новый платный разбор.

### Пакет анализа: New Run… → Error Analysis Batch

Форма:

- **Project** — **All projects**, проект, к которому привязаны сессии, или папка, где они шли. Число рядом — сколько сессий с 5+ запросами.
- **Period** — галочки **From** и **To** с датами.
- **Sessions from** — **All harnesses**, **Claude Code** или **Pi**: только сессии, которые вёл этот харнесс. Нужен для проекта, где есть и сессии Claude Code, и сессии Pi, а политика разрешает каждому получать только свои.
- **Sessions** — размер выборки, по умолчанию 20 (до 200).
- **Notes by** — **Automatic** или **Choose…** (тогда **Harness**, **Model**, **Effort**). Automatic берёт модель другого семейства, чем у большинства подходящих сессий, если такая настроена и политика разрешает её для источника каждой сессии; иначе Claude Code с вашими настройками, если политика разрешает его. Если ни один адресат не разрешён для всех сессий, пакет ведёт тот, кому разрешено больше всего, а остальные сессии убираются из выборки до её отбора: перед постановкой AKit скажет, сколько их (ниже). Пакет не ставится, только если ни одному адресату нельзя ни одной сессии. **Choose…** оставляет все сессии; если политика откажет выбранной модели в части из них, AKit тоже сначала спросит.
- **Matching model** — модель для сопоставления и кластеризации; пусто — та же, что для заметок.
- **Language** — язык абзаца и советов (по умолчанию из Settings).
- Строка оценки: «N sessions, ≈ $X …» или «no estimate yet». При **Automatic** оценка считается по вашей модели Claude Code («the reviewer is picked when the sample is drawn»). Если под фильтр не подходит ни одна сессия, вместо оценки «No sessions of the index match: …», а **Sample and Queue** серая.
- **Open in** — **Automatic**, Orca, herdr или Background (под формой).

**Sample and Queue**:

1. Пересчитываются дешёвые сигналы сессий индекса (локально).
2. При **Automatic** выбирается модель заметок, и сессии, которые ей слать нельзя, убираются из выборки.
3. Выбирается выборка: четверть случайно, остальное поровну по слоям «харнесс | семейство модели | сильнейший сигнал». Сессии, в которых поштучные разборы нашли проблемы, подсказывают слои для дополнительного выбора. У каждой сессии записывается вероятность включения.
4. Если сессии убраны (Automatic) или политика откажет выбранной модели в части выборки (**Choose…**), появляется окно подтверждения: «Sessions Left Out» («N sessions of the filter are left out of the sample: …») или «Sessions the Policy Refuses» («N of the M sampled sessions may not go to …»). **Queue N Sessions** ставит именно эту выборку, **Cancel** — ничего не ставит. Отказанные сессии при **Choose…** не отправляются и получают `error`, поэтому отчёт покроет меньше сессий; лучше сузить выборку через **Sessions from**.
5. Проверяется месячный лимит с оценкой. Если не проходит — ошибка в окне, ничего не ставится.
6. Пишется `batches/<run-id>.json` и ставится Lab-запуск.

Выборка фиксируется сразу, поэтому запуск и отчёт всегда про одни и те же сессии.

> **Совет:** если при **Automatic** нужен конкретный вид сопоставления, лучше выберите модель заметок явно через **Choose…**. При Automatic поле **Matching model** применяется к Claude Code с вашими настройками, даже если заметки пойдут через Pi.

### Страница пакета в Lab

Блок **Batch**:

- Строка-сводка: выборка (сколько взято из скольких запрошенных, seed) или «Fixed sessions» для стартового набора, проект, «Pi sessions» или «Claude Code sessions» (если выбран **Sessions from**), период, кто пишет заметки, кто сопоставляет, сколько сделано, сколько с ошибкой и сколько «too long for a digest», «N left out before sampling: …» (если Automatic убрал сессии), оценка при постановке.
- Прогресс по шагам: **Notes**, **Verifier**, **Matching**, **Judges** (если есть судьи), **Clustering** (done / not yet и число кандидатов).
- Красная плашка «The worker paused the batch: …» — пакет сам остановился (например, после ошибки авторизации аккаунт сменился или не определился). Разберитесь с причиной и нажмите **Resume**.
- Оранжевая «Paused: …» — пакет на паузе по вашей просьбе.

Кнопки:

- **Pause** (пока запуск идёт или ещё стоит в очереди) — пишет флаг паузы в пакетный файл. Пакет больше не берёт новые сессии, а уже начатые доводит до конца (все шаги). Конец пакета (код-проверки, кластеризация) на паузе не выполняется. В ожидание сессии возвращаются только при **Cancel** или при перезапуске умершего запуска.
- **Resume** (когда запуск не идёт и есть недоделанное) — ставит новый Lab-запуск того же пакета; он продолжит с того же места.
- **Retry Errors** (когда есть сессии с ошибкой) — переводит ошибочные сессии обратно в ожидание и ставит новый запуск. Старый результат сессии удаляется, только когда повтор удался. Сессии `too-long` не повторяются: повтор их не уместит, а деньги не тратятся. Если старый запуск ещё жив, он не вернёт повторяемые сессии в `error` и может сам их подхватить.
- У **Resume** и **Retry Errors** справа стрелка-меню: «Resume in Orca», «Resume in herdr», «Resume in Background» (и так же для **Retry Errors**) — где откроется вкладка нового запуска. Простой клик по кнопке открывает её там, где AKit предлагает сам (как **Automatic** в **Open in**).
- **Open Report** (когда хоть одна сессия готова) — переход на **Error Analysis** → **Reports** с этим пакетом.

Блок **Sessions**: у каждой сессии **Status** (`pending`, `running`, `done`, `error`, `too-long` — пользовательские реплики и ошибки инструментов одни не влезают в бюджет дайджеста модели, сессия не отправлялась), название и сообщение об ошибке, **π** (вероятность включения), **Sampled** (`random`, слой или `fixed` у пакета стартового набора), **Last step** (при наведении — все шаги) и кнопка **Show Notes**, когда шаг заметок у сессии уже прошёл. Она открывает окно заметок сессии (ниже).

Как идёт пакет:

1. Проверка аккаунтов один раз в начале; источник каждой сессии проверяется на каждом вызове.
2. По две сессии одновременно: заметки → проверка → сопоставление → судьи активных режимов. Ошибка лимита запросов (429, «rate limit», «too many requests», «overloaded») повторяется с растущей паузой (10, 20, 40, 80 секунд), до 4 раз. Неверный ответ модели — ошибка сессии, а не пропуск. Ошибка судьи тоже: сессия получает статус `error`, и **Retry Errors** осудит её снова. Сессия, слишком длинная для дайджеста заметок, получает `too-long` и считается отдельно от ошибок; слишком длинная для судьи — остаётся `done` без вердикта этого судьи.
3. После ошибки авторизации аккаунты заметок, сопоставления и судей проверяются снова; если какой-то сменился или не определяется, пакет встаёт на паузу.
4. Когда всё готово: код-проверки активных режимов по индексу, запись совпадений семян (два пакета с двумя разными сессиями активируют семя), повышение кандидатов, которых это сопоставление нашло снова, кластеризация заметок без режима в новых кандидатов (заметки сессий, которые адресату слать нельзя, остаются в стороне, и вывод запуска пишет «Clustering: N of M notes left out: …»), выбор 8 заметок для выборочной проверки.

Если конец пакета не удался, пакет пишет «The end of the batch failed: … Resume the batch to try again» — кнопка **Resume** доделает только этот конец.

### Окно заметок сессии

Открывается кнопкой **Show Notes** у сессии пакета, **Show Session Notes** у заметки на странице режима и **Show Session Notes** у сессии в ячейке матрицы переходов. Это то же, что `akit analysis notes SESSION`, плюс сигналы и маршруты. Сверху название и ключ сессии, ниже:

- карточка итога (без размера сессии), **What to Change**, **Problems by Type** и свёрнутые **Details** — как на странице поштучного разбора;
- **Routes** — куда сейчас отнесена каждая принятая заметка модели: режим или «None fits», уверенность и «accepted by you», «rejected by you», «moved by you» или «waits for you on the Review tab»;
- **Signals** — дешёвые сигналы сессии, посчитанные кодом прямо здесь по транскрипту, без вызова модели: **Interrupted**, **Pushbacks**, **Rejected**, **Tool errors**, **Repeated calls**, **Done with no check**, **User turns**, **Steps**. Поднятые сигналы выделены оранжевым. Четыре из них считаются по тем же правилам, что и в Lab (вкладка **Analysis** у сессии). **Interrupted** — ваши сообщения, которые начинаются с `[Request interrupted by user`; эта строка внутри другого текста не считается, сообщения субагентов тоже. **Rejected** — вызовы, от которых отказались вы, правило разрешений, hook, классификатор auto mode или расширение Pi; Esc на запросе разрешения считается прерыванием, а не отказом. **Tool errors** — вызовы, которые закончились ошибкой, без отказов и прерываний. **Repeated calls** — серии из 3 и более вызовов подряд одного инструмента с одним и тем же вводом; серия считается один раз, сколько бы вызовов в ней ни было, а другой вызов между ними серию обрывает. Если транскрипта уже нет на диске, вместо них «The transcript can't be read: …».

Кнопки сверху справа:

- **Show Review Run** (или **Show Run in Lab** для пакета) — открывает Lab-запуск, который написал эти заметки, если он ещё есть. У окна, открытого со страницы самого пакета, этой кнопки нет.
- **Route Again…** — то же, что `akit analysis route SESSION`: окно отправки с моделью и оценкой «≈», затем принятые заметки сессии вместе со списком режимов и их примерами уходят сопоставлению. Маршруты, которые вы уже рассмотрели, сохраняются. Если заметки, проверяющий, модель сопоставления и список режимов те же, что при прошлом сопоставлении, ничего не отправляется и AKit так и пишет. Серая, если принятых заметок нет. Маршруты с уверенностью ниже 0.6 после этого ждут вас на вкладке Review.

### Контрольная ячейка в Lab

Страница ячейки: блок **Control task** (репозиторий и коммит, оракул, источник, настройка, «Repeat i of n», путь к клону, если он сохранён) и блок **Oracle**: **Passed** или **Failed**, текст оракула, «The mode shows at #…», и флаги охраны:

- «Flagged: comparisons count this cell as failed»;
- «Fewer tests than before the agent ran»;
- «Test files changed: …»;
- «The agent's tool calls read …» (исходная сессия, история сессий, настоящий репозиторий; у задачи из коммита ещё «the commit …» и «AKit's Lab folder»).

У ячейки задачи из коммита текст оракула — «hidden tests: 1/1 fail-to-pass, 1/1 pass-to-pass», а ниже блок **Hidden tests**, как у replay: **Fail-to-pass**, **Pass-to-pass**, упавшие тесты и примечание, если тесты не собрались после агента.

Без флагов: «Guard: the test count didn't drop, no test file changed, no sign the agent read the exemplar». У ячейки оценки слоя настройка называется «layer СЛОЙ@коммит», «without СЛОЙ@коммит» или «read-only · without СЛОЙ@коммит», а под охраной — заметки о том, куда лёг слой (например, «The layer's AGENTS.md section is appended to the project's own CLAUDE.md.»). Если таких заметок нет у ячейки слоя, её выполнила старая команда `akit`, которая слой проигнорировала: «Run by an akit that ignored the layer: left out of comparisons. Install the app and akit together.» Строка «Claude Code X.Y.Z» — версия, с которой шла ячейка. Ниже, как у всех запусков агента, — метрики сессии самого агента.

### Lab → Sends

Переключатель **Runs** / **Sends** в панели инструментов Lab. **Sends** — журнал всех вызовов, которые отправили данные сессий или код, новые сверху:

- **Date**, **Purpose** (`notes`, `verifier`, `matching`, `clustering`, `retro-matching`, `pairing`, `similar-cases`, `judge`, `control`, `review`, `replay`);
- **Destination** — харнесс · провайдер · аккаунт (при наведении ещё организация);
- **Model** («default», если модель не задана), **Tokens in / cached / out**, **Cost** (прочерк, если харнесс не записал стоимость), **Session**.

Внизу: «This month: $X recorded · limit $Y · N sends».

Журнал перечитывается при каждом открытии, при изменении запусков и когда меняется сам файл журнала: вызовы с экрана Error Analysis и из `akit` в терминале появляются здесь через пару секунд.

Все поля сохраняются сразу при изменении в `~/.akit/lab/settings.json`. Тот же файл читает `akit lab policy`. Если файл есть, но не читается (испорчен JSON или, например, лимит записан не числом), AKit ничего не отправляет: «Not sent: … settings.json can't be read, so the allowed list, your scrub patterns and the monthly limit can't be checked. Fix or move the file, then try again». Иначе по умолчанию пропали бы список разрешённых, шаблоны маскирования и месячный лимит.

### Review language

Язык абзаца и советов новых разборов и пакетов: English, Russian, Czech. Тексты AKit остаются английскими. Язык входит в ключ готовности заметок: при смене языка уже разобранные сессии при следующем разборе перепишутся заново (это стоит денег).

### Sending policy

Вверху строка режима: «Work Mac: session data goes back to the harness and provider that recorded it, plus your company's allowed list» или «Personal Mac: session data goes back to the harness and provider that recorded it, plus the allowed list». Правило одно на обоих Mac: данные можно вернуть тому агенту и провайдеру, который их записал (у него они уже есть), а всё остальное — только адресатам из списка. На рабочем Mac список составляйте по правилам компании. Сам выбор Personal/Work хранится не здесь, а в `~/.akit/machine.json` (Settings → **This Mac**).

Список разрешённых адресатов: каждая запись — «харнесс · провайдер · аккаунт · план или организация». Кружок с минусом убирает запись.

**Add Destination…** — окно: **Harness**, **Provider** (меню **Providers**: для Claude Code `anthropic`, `bedrock`, `vertex`; для Pi — провайдеры из `pi --list-models`), **Account**, **Plan or org**. Все поля обязательны. **Add**. Данные сессий из любого источника смогут уходить этому адресату.

**Check Accounts** — для каждого установленного харнесса с его моделью по умолчанию: у Claude Code вызывается `claude auth status --json` (аккаунт, организация, провайдер, без секретов), у Pi берётся ваша запись и `pi auth check`. Для каждого показывается адресат (зелёная галочка) и вердикт для собственных сессий этого харнесса: «allowed (on the list)», «allowed (same origin)» или «not allowed. …». Если аккаунт не определился — оранжевая строка с причиной. Ничего не отправляется.

**Add to List** у проверенного аккаунта — добавить его в разрешённые одним нажатием.

> **Совет:** заполняйте список по правилам компании для данных сессий, а не только для кода. Сессии содержат ваши запросы, пути, вывод команд.

### Pi accounts

Pi не умеет сказать, под каким аккаунтом он вошёл к провайдеру. Поэтому аккаунт и план/организацию вы вводите сами: **Add Pi Account…** → **Provider** (например, `github-copilot`), **Account**, **Plan or org** (для Copilot — организация, которая его выдаёт). Карандаш правит запись, минус удаляет. **Add Pi Account…** для провайдера, у которого запись уже есть, заменяет её. Запись нужна только для списка разрешённых: по ней AKit сверяет адресата со списком. **Add Destination…** с **Harness** Pi создаёт её сам, если для провайдера записи ещё нет. Без записи сессия Pi уходит только тому провайдеру, который её записал, на любом Mac (как у Claude Code: подходит аккаунт, под которым агент вошёл). AKit никогда не читает ключи Pi. Если вы переключили аккаунт внутри Pi, AKit этого не увидит: запись — на ваше доверие.

### Masked before sending

Перед любой отправкой текст проходит маскирование:

- всегда: правила gitleaks, перенесённые в Swift (ключи AWS, GitHub, GitLab, Slack, Stripe, Google, Anthropic, OpenAI, приватные ключи и т. п.), общее правило «имя похоже на секрет = значение», флаги вида `--token VALUE`, строки `.env` с секретными именами, детектор случайных строк по энтропии. Значение после имени пароля (`db_password: Summer2024`, `--password hunter22`, `PGPASSWORD=…`, `password: 123456`, `password=letmein`, `IDENTIFIED BY '…'` и `PASSWORD '…'` в SQL, `mysql -pSecret`) маскируется, даже если оно слабое: без порога энтропии, от 4 символов, если только оно не похоже на код (переменная вроде `input2`, путь, тип, плейсхолдер вроде `<PASSWORD>`) или на текст о флаге («the `--password` flag»). Слово без цифр маскируется только сразу после `=` без пробела, а `-p…` — только после `mysql`, `mysqldump` и `mysqladmin`. Маскирование на экране AKit работает по тем же правилам ключей и паролей. Хеши, SHA и UUID без секретного имени не трогаются. Найденные ключи никогда не проверяются онлайн;
- **Mask e-mail addresses** (включено по умолчанию) — адреса заменяются на `[email hidden]`;
- **Internal host patterns** — регулярные выражения, по одному на строку, без учёта регистра; совпадения становятся `[host hidden]`;
- **Other patterns** — любые другие выражения; совпадения становятся `[secret hidden]`.

Неверные выражения показываются красным и пропускаются. Внизу номер версии маскирования. Версия входит в ключ готовности: при её смене заметки перепишутся.

> **Важно:** ключ готовности считается от уже замаскированного транскрипта. Если новый шаблон хоста или e-mail что-то находит в сессии, её вход меняется, и следующий разбор перепишет заметки заново (это стоит денег).

> **Важно:** это обновление подняло версию маскирования до 4 (слабые пароли). Поэтому следующий разбор каждой уже разобранной сессии — в пакете, в **Queue Model Notes…** или поштучно — один раз заново пишет заметки и проверку. Это платно; форма пакета и окна отправки показывают оценку «≈» до отправки. Вердикты судей при этом не стираются: каждый вердикт помнит версию маскирования, по которой судили, и старые вердикты продолжают считаться в отчётах, проверке судей и оценке фиксов, пока сессию не осудят снова. Вердикты, сделанные до того, как версия стала записываться, считаются актуальными и заново не судятся (они по-прежнему верны для той же сессии, а повторный суд всех сессий стоил бы денег).

### Cost

**Monthly limit (US dollars)** — пусто значит без лимита. Значение сохраняется, только когда оно читается как сумма (например, `20` или `12.50`); иначе под полем красная подсказка, а в файле остаётся прежний лимит. Перед каждым вызовом модели AKit складывает записанную стоимость текущего календарного месяца и оценку этого вызова. Если сумма больше лимита, вызов не делается: «Not sent: the monthly limit is $X, $Y is recorded this month and this needs ≈ $Z. Raise it in Settings → Lab». **Recorded this month** — сколько записано за месяц. Лимит общий для всего, что AKit отправляет моделям.

## Как считается каждая цифра
<!-- section: numbers -->

### Заметки и частоты — это разное

- Заметка — одно наблюдение модели (или ваше) в одной сессии.
- «Seen in k notes» — сколько принятых проверяющим заметок модели сейчас отнесено к режиму. Маршрут с уверенностью ниже 0.6 входит только после вашего **Accept**. Ваши заметки стартового набора сюда не входят. В таблице Modes считается по всему пулу, в отчёте — по сессиям пакета.
- Частота — доля сессий пакета, где проверка режима сказала «есть». Только из проверки, прогнанной по всем сессиям пакета, с весами выборки.

Пример: в пакете из 20 сессий модель написала 12 заметок про «Steps repeated without progress» в 5 сессиях. «Seen in 12 notes» говорит только, что режим встречался. А код-проверка этого режима сказала «есть» в 6 сессиях из 20: частота 6/20 = 30% до весов. Пять сессий с заметками в частоте не участвуют вообще. И показывается эта частота, только если проверка точна или провалидирована.

> **Почему так:** цепочка «модель заметила → модель отнесла к режиму» умножает ошибки двух моделей и не даёт знаменателя: сессия, где модель ничего не заметила, не значит «режима нет». Проверка выносит вердикт по каждой сессии, и её ошибки можно измерить.

### Проверки: mechanical, heuristic, judge

- **Mechanical** — проверка и есть определение режима («файл > 20 КБ прочитан без диапазона»). TPR = TNR = 1 относительно определения. Доверие `exact`, без поправок. Интервал покрывает только случайность выборки.
- **Heuristic** — код, который только приближает смысловой режим («готово» без проверки после правки как признак преувеличения). Пока не провалидирован, режим показывается как «seen in k notes».
- **Judge** — LLM-судья. Тоже нужна валидация.

### Веса выборки (Horvitz–Thompson)

У каждой сессии пакета записана вероятность включения π:

π = r / M + n_h / N_h (но не больше 1),

где M — число подходящих сессий, r — число случайных выборов (четверть размера пакета), N_h — размер слоя сессии, n_h — сколько из слоя выбрано по слоям.

Пример: подходящих сессий M = 200, пакет 20, случайно r = 5. Слой «claude | claude-opus | pushback» из 10 сессий получил 3 выбора: π = 5/200 + 3/10 = 0.325. Слой «quiet» из 150 сессий получил 3: π = 0.025 + 0.02 = 0.045.

Взвешенная доля = Σ(1/π по положительным) ÷ Σ(1/π по всем).

Пример: четыре сессии. Две «шумные» с π = 0.8 (вес 1.25), обе положительные. Две «тихие» с π = 0.2 (вес 5), обе отрицательные. Простая доля 2/4 = 50%. Взвешенная (1.25 + 1.25) / (1.25 + 1.25 + 5 + 5) = 20%. Шумные сессии выбирались чаще, и вес возвращает их к настоящей пропорции.

Колонка **Plain** показывает долю без весов рядом.

### Поправка на ошибки проверки (Rogan–Gladen)

Только для провалидированной проверки. Если проверка знает свои TPR и TNR, наблюдаемую долю p_obs можно поправить:

θ = (p_obs + TNR − 1) / (TPR + TNR − 1), обрезано до [0, 1].

Пример: p_obs = 20%, TPR = 0.90, TNR = 0.95. θ = (0.20 + 0.95 − 1) / (0.90 + 0.95 − 1) = 0.15 / 0.85 ≈ 17.6%. Проверка немного завышала из-за ложных срабатываний.

Если p_obs ≤ 1 − TNR (здесь ≤ 5%), отчёт пишет «Below detection threshold»: такую долю нельзя отличить от ложных срабатываний.

### Интервалы

- В отчёте: 95% интервал бутстрепом, 1000 повторов. Сессии пакета пересэмплируются внутри своих групп выбора (`random` и каждый слой). Группы, где меньше двух сессий, сливаются в одну: одна сессия, пересэмплированная сама с собой, никогда не меняется, и интервал вышел бы слишком узким. Для провалидированной проверки пересэмплируются и тестовые метки, на которых измерены TPR и TNR, и каждый повтор поправляется заново. Поэтому интервал учитывает и неуверенность в самой проверке.
- «k of n (95% a–b%)» на странице режима и в таблице Modes — интервал Wilson.
- В «до/после» — Wilson для каждой стороны.

Интервал Wilson для k успехов из n:

- 18/20 → 70–97%;
- 28/30 → 79–98%;
- 29/30 → 83–99%;
- 46/50 → 81–97%.

### Валидация: когда проверке можно верить

- Метки: ваш стартовый набор через сопоставление заметок (лучший источник), принятые и отклонённые находки похожих случаев, решённые сложные случаи. На одну сессию одна метка, стартовая важнее остальных.
- Разбиение по хешу: 10% train, 30% dev, 60% test. Делается при каждом запуске валидации: уже разложенные сессии остаются на месте, новые раскладываются, сессии примеров переносятся в train. Примеры и образцы для судьи — только из train.
- На dev итерируйте сколько угодно. Test — один раз на версию режима и проверку.
- TPR — доля положительных сессий, где проверка сказала «есть». TNR — доля отрицательных, где сказала «нет». Сложные случаи без вашего решения не входят.
- **validated**: нижняя граница Wilson и для TPR, и для TNR не ниже 80%, и на каждый класс (есть / нет) не меньше 30 тестовых меток.
- **provisional**: 20+ тестовых меток на класс, но граница не пройдена (или меток меньше 30). Отчёт показывает «seen in k notes» и рядом долю проверки с пометкой «not a frequency».
- **not validated**: всё остальное.

Пример: TPR 29/30 → нижняя граница 83.3%; TNR 28/30 → 78.7%. По TNR не прошла: `provisional`. Нужно 29/30 и там, и там, или около 46/50.

> **Почему так:** по одной точке нельзя: судья с 90% на 20 метках может на деле иметь 70%. Нижняя граница честнее. А простое «совпадение в 80% случаев» вообще не годится: судья может совпадать в 80%, пропуская большинство настоящих отказов, если они редки.

Любое изменение смысла режима (правка, слияние, разделение), смена харнесса, модели или промпта судьи, смена версии код-проверки делает результаты недействительными: учитывается только тест текущей версии режима с текущей проверкой.

### Seen in k notes вместо процента

Отчёт показывает процент только при доверии `exact` или `validated`. Во всех остальных случаях — «Seen in k notes». Это не недоработка, а правило: без измеренной проверки процент был бы выдумкой.

### Активация семян и повышение кандидатов

- Семя становится активным, когда два разных пакета своим собственным сопоставлением отнесли к нему заметки, и за этими совпадениями стоят как минимум две разные сессии. Пример: пакет 1 отнёс к семени заметку из сессии X, пакет 2 — из сессии Y → семя активно. Если оба пакета нашли его только в X — нет. Поштучные разборы не считаются. Маршруты, унаследованные от прошлых разборов, тоже не считаются. А вот маршруты с низкой уверенностью, которые вы ещё не рассматривали, считаются.
- Кандидат становится режимом, когда маршрут к нему получила сессия, не входившая в те, из которых его сделала кластеризация (через сопоставление, ретро или ваш перенос), и всего сессий у него не меньше двух.

### Насыщение и пересборка

- Доля без режима = заметки пакета, текущий маршрут которых «ничего не подходит», ÷ все маршрутизированные заметки пакета.
- Пересборка предлагается при доле больше 15% или каждый пятый пакет.
- Список насыщен, когда доля без режима и число новых режимов несколько пакетов подряд около нуля.

### Матрица переходов

- Фазы считает код по инструментам: Read, Grep, Glob, веб-поиск → Explore; Edit, Write → Edit; Bash с тестами, сборкой или линтером и браузерные инструменты → Verify; прочий Bash по команде (чтение → Explore, запись → Edit); последнее сообщение ассистента → Report; всё остальное наследует фазу предыдущего шага (до первого инструмента — Understand). Модель может пометить только Understand и Plan.
- Колонка — фаза решающего шага (метка модели Understand/Plan, если она есть у заметки этого шага, иначе фаза по коду). Строка — фаза шага прямо перед ним, а для результата инструмента — шага перед его вызовом.
- Сессия без принятых заметок → ячейка Report → No failures.
- Сессия с заметками, но без решающего шага → вне матрицы.
- Разница двух матриц: изменение доли ячейки; «в пределах шума», если p Фишера ≥ 0.05; бледная, если с обеих сторон меньше 3 сессий.

### Полнота и точность стартового набора

Пример: в 10 сессиях с подтверждёнными парами вы записали 10 проблем. В парах с принятыми заметками модели из них 7 → полнота 70%. Проверяющий принял 12 заметок модели, вы отметили 9 как настоящие → точность 75%. Если ещё одна ваша проблема в паре только с заметкой, которую проверяющий отклонил, она идёт только в **Before verifier**: 8 из 10 = 80% до проверяющего против 70% после.

### Правило «помогло» в реальной работе (до/после T)

Окна: «после» — от T до сейчас, «до» — столько же времени до T (минимум сутки). Только сессии с вердиктом проверки.

- P(after < before) считается точно для апостериорных Beta(1,1): каждая сторона — Beta(отказы + 1, успехи + 1).
- `helped`: P(after < before) ≥ 0.95 и P(after > before) ≤ 0.5.
- `no conclusion`: меньше 15 сессий с какой-то стороны.
- `not shown`: остальное.

Примеры (до: 12 отказов из 30):

- после 3 из 30: P(after < before) = 0.996, Фишер p = 0.015 → `helped`;
- после 8 из 30: P = 0.858, p = 0.41 → `not shown`, хотя «стало меньше».

Минимальный заметный эффект: самое низкое значение «после», которое при таком числе сессий с каждой стороны можно отличить от «до» с мощностью 80%. Пример: при 50% до и 30 сессиях с каждой стороны заметно только падение примерно до 17%. Чтобы заметить 20% → 5%, нужно около 70 сессий с каждой стороны.

> **Почему так:** обычные интервалы по центральной предельной теореме занижают неуверенность при 15–50 сессиях на группу. Поэтому байесовское правило, и поэтому порог 15.

### pass@1, pass^k и «помогло» на контрольных задачах

Пример: три задачи по 3 повтора. Задача A 3/3, B 2/3, C 0/3.

- pass@1 = (1 + 0.667 + 0) / 3 ≈ 56%.
- k = 3. pass^3 = доля задач, где прошли все 3: A да, B нет, C нет → 33%. (Если у задачи больше k ячеек, берётся несмещённая оценка C(прошло, k) / C(всего, k).)

Парное сравнение: для каждой задачи изменение доли «вариант − база», затем бутстреп по задачам (2000 повторов), доля повторов, где среднее изменение больше нуля. Пример: база A 1/3, B 0/3, C 2/3; вариант A 3/3, B 1/3, C 2/3. Изменения +0.67, +0.33, 0, среднее +0.33. Доля бутстрепа на улучшении около 96% (не на улучшении только повторы из одной C). Но ячеек 9 с каждой стороны, меньше 15 → `no conclusion`. Нужно больше задач или повторов. И даже с 15+ ячейками `helped` требует ещё «не хуже в реальной работе» по сессиям после T.

21 из 30 против 25 из 30 — p Фишера ≈ 0.36: это совместимо с шумом. «+4 ячейки» ничего не доказывают.

## Деньги, отправка и маскирование
<!-- section: money -->

### Что и куда уходит

Каждый вызов модели анализа (заметки, проверка, сопоставление, кластеризация, ретро, пары, похожие случаи, судья) проходит одну точку (`ModelCall`):

1. Проверка политики для каждого источника данных в вызове. Вызов над заметками многих сессий несёт источники их всех. Кластеризация, ретро, первые режимы и похожие случаи заранее убирают заметки сессий, которые адресату слать нельзя (и говорят, сколько убрано), а примеры режимов убираются так же в сопоставлении и у судьи. Если в вызове всё же остался неразрешённый источник, вызов не делается.
2. Маскирование (см. Settings).
3. Проверка месячного лимита с оценкой этого вызова.
4. Вызов через харнесс без инструментов, без ваших настроек и без сохранения сессии. У Claude Code: `--tools ""`, `--safe-mode`, `--strict-mcp-config`, схема ответа. У Pi: `--no-tools`, `--no-skills`, `--no-context-files`, `--offline`.
5. Запись в журнал: дата, назначение, сессия, запуск, адресат, модель, число отправленных символов, токены, записанная стоимость, версия маскирования, сколько совпадений каждого правила замаскировано (сами значения никогда). Неудачный вызов тоже записывается, если харнесс записал его стоимость.

Запуски агентов (контрольные ячейки, разборы **Agent with file tools**, повторы коммитов) через эту точку не идут. Политика проверяется так же, но маскируется только промпт или транскрипт сессии, а код репозитория уходит агенту как есть. Лимит сверяется только с уже потраченным, без оценки этого запуска. У агента есть инструменты.

Что уходит при каждом действии:

- **Заметки** — дайджест транскрипта: реплики пользователя дословно, длинный вывод инструментов с началом, концом, кодом выхода и строками ошибок. Бюджет около 90K токенов (360K символов), для моделей с окном 1M (и семейств GPT и Gemini) около 250K токенов. Если одни реплики пользователя и ошибки инструментов (их никогда не режут) больше бюджета, сессия не отправляется вовсе: ошибка «The session is too long for one call» (у судьи — «too long for one judge call») с советом взять модель с окном 1M.
- **Проверка** — для каждой заметки с найденной цитатой: шаг (до ~6000 символов вокруг цитаты), по три шага до и после (по 1200 символов), все реплики пользователя.
- **Сопоставление** — принятые заметки сессии и список режимов с примерами. Без транскрипта.
- **Кластеризация**, **ретро**, **похожие случаи**, **пары**, **первые режимы** — заметки (описания и цитаты), без транскрипта. Но цитаты — это куски транскрипта, поэтому политика действует.
- **Судья** — дайджест транскрипта и описание режима.
- **Контрольная ячейка** — промпт задачи и весь код репозитория, с которым работает агент.

### Оценки «≈»

- Окно отправки (кластеризация, ретро, пары, первые режимы, похожие, судья): записанная стоимость одного символа прошлых вызовов той же модели того же харнесса × размер отправки. Размер у судьи — грубо 60 000 символов на сессию.
- Пакет: средняя записанная стоимость заметок + проверки + сопоставления на одну разобранную сессию этой моделью × число сессий, плюс средняя стоимость вызова судьи для каждого включённого судьи активного режима.
- Ячейки: средняя записанная стоимость прошлых контрольных ячеек той же модели × число ячеек.

«No estimate yet» значит: этой моделью ещё ничего не записано. Один разбор сессии даёт оценку для окон отправки и формы пакета, но только для того же харнесса и точно того же имени модели. Оценка ячеек появится только после первой контрольной ячейки этой модели.

### Что сколько вызовов делает

- Разбор сессии: 1 вызов заметок, 1 вызов проверки (если есть заметки с найденными цитатами), 1 вызов сопоставления (если есть принятые заметки и режимы).
- Пакет из N сессий: до 3N вызовов, плюс N на каждого судью, плюс 1 вызов кластеризации в конце.
- **Retro-match…**: 1 вызов на каждые 60 заметок пула.
- **Find Similar Cases…**: 1 вызов на каждые 80 заметок.
- **Propose Pairs…**, **First Modes…**, **Cluster Unmatched Notes…**, **Cluster All Notes Again…**: 1 вызов.
- **Run Judge over the Pool…**, **Validate on Dev…** / **Test…** с судьёй: 1 вызов на сессию (уже осуждённые тем же судьёй на неизменённом файле при той же версии маскирования пропускаются).
- Ячейка: целый прогон агента — самое дорогое.
- Бесплатно и локально: **Run Check**, **Pick Sessions…**, разметка, сопоставление своих заметок, решения на Review, валидация эвристической код-проверки, **Check Reference**, создание задач, отчёты.

### Ключ готовности: когда платить второй раз не придётся

Для каждого шага AKit хранит ключ: хеш входа + хеш настроек этого шага и всех шагов, чей результат он читает (харнесс, модель, версия промпта, версия маскирования, усилие, язык; у заметок ещё числа AKit — ровно то, что уходит модели: их считает сам шаг заметок только по транскрипту Claude Code (без git, то есть без того, попал ли коммит потом в основную ветку) и маскирует как транскрипт, поэтому разбор из Lab и пакет делят одни заметки; название сессии модели не отправляется; у сопоставления ещё версия списка режимов — хеш их определений и критериев, без примеров). Если ключ есть — шаг пропускается. Вход считается от уже замаскированного транскрипта, поэтому новый собственный шаблон маскирования, который что-то находит в сессии, тоже меняет ключ.

- Повторный разбор той же сессии той же моделью: заметки и проверка не вызываются.
- Сессия продолжилась (файл вырос) — новый вход, заметки пишутся заново. Ваши решения о маршрутах переносятся на новые заметки с тем же шагом и той же цитатой.
- Поднялась версия маскирования — меняется вход, заметки и проверка всех сессий проходят заново при следующем разборе. Судья заново судит сессию, когда до неё дойдёт пакет, прогон по пулу или проверка; до того её старый вердикт считается.
- Переименовали режим или поправили его определение — меняется только ключ сопоставления. Слепые заметки не переписываются.
- Сменили модель заметок — переписываются заметки, проверка и сопоставление, но не судьи и не код-проверки.

### Месячный лимит и журнал

Лимит общий для всего: разборы, пакеты, пары, похожие случаи, судьи, ретро, ячейки, повторы коммитов. Считаются только стоимости, записанные харнессами. Журнал — Lab → **Sends** и `~/.akit/lab/analysis/sends.jsonl` (только дописывается, никогда не переписывается).

## Где что хранится и команды CLI

### Файлы

Всё локально, ничего не попадает в мозг (brain).

```
~/.akit/lab/analysis/            локальный git-репозиторий без remote; отслеживает только modes/
  modes/modes.json               режимы: определения, версии, статусы, фиксы, слияния
  modes/exemplars/<mode>.json    примеры (цитаты)
  notes/<session-key>.json       разбор сессии: исход, заметки, вердикты, маршруты, советы, ключи
  checks/<mode>.json             вердикты код-проверки по сессиям индекса
  checks/<mode>@judge.json       вердикты судьи
  labels/reservations.json       зарезервированные сессии стартового набора
  labels/bootstrap/<key>.json    ваша разметка
  labels/pairs/<key>.json        пары заметок
  labels/book.json               сопоставление ваших заметок, находки, выборочные проверки, сложные случаи
  labels/unclear.json            корзина Unclear
  labels/splits.json             разбиение train/dev/test по режимам
  labels/validation.json         результаты валидации
  labels/judges.json             кто судит какой режим
  batches/<run-id>.json          пакеты: выборка, вероятности, статусы, кандидаты
  fixes/<mode>.json              черновики фиксов
  work/                          временные входные файлы вызовов с экрана Error Analysis
  sends.jsonl                    журнал отправок
~/.akit/lab/<run-id>/            Lab-запуски (разборы, пакеты, ячейки)
~/.akit/lab/evals/tasks/<id>.json  контрольные задачи
~/.akit/lab/evals/sets/<layer>.json  наборы слоёв: задачи и ответы на поля
~/.akit/lab/evals/layer-evals/<id>/  оценки слоёв: манифест и файлы слоя

~/.akit/index/index.sqlite       индекс сессий (и таблица сигналов)
```

Коммит в репозитории режимов делает каждое: добавление, переименование, правка, область, слияние, разделение, отклонение, восстановление, подтверждение, запись совпадения пакета, смена статуса фикса, добавление и удаление примера. Всё вне `modes/` git игнорирует, поэтому заметки, метки и вердикты никогда не попадают в историю. Исключение — примеры: их цитаты лежат в `modes/exemplars/` и есть в локальной истории git (без remote), а в сообщениях коммитов о примерах стоят ключ сессии и номер шага. История — кнопка **History** или `akit analysis mode history`.

Каждый файл папки меняется под блокировкой как «прочитать с диска — изменить — записать». Приложение, `akit` и два работника пакета не затирают изменения друг друга.

### Команды, которые повторяют кнопки

- Режимы: `akit analysis modes [--all]`, `akit analysis mode show|rename|edit|merge|split|reject|restore|confirm|scope|exemplar|history …`.
- Модель: `akit analysis cluster [--rebuild]`, `akit analysis retro MODE`, `akit analysis route SESSION` (**Route Again…**).
- Очередь: `akit analysis queue`, `akit analysis accept|reject SESSION#NOTE [--move MODE|none]`, `akit analysis spot SESSION#NOTE agree|disagree`, `akit analysis unclear SESSION#NOTE [--remove]`.
- Стартовый набор: `akit analysis bootstrap pick|list|label|pair|confirm|metrics|first-modes|notes|map|similar|find …`.
- Пакеты: `akit lab new analysis [--project …] [--from …] [--to …] [--size N] [--session-harness claude-code|pi] …`, `akit analysis batch list|show|pause|resume [--retry-errors] [--env …]`. `--session-harness` — как **Sessions from** (не путать с `--harness`, который выбирает модель заметок). Без `--yes` команда печатает число сессий, модель заметок, оценку и предупреждение о сессиях, убранных из выборки или отказанных политикой; с `--yes` ставит пакет (выборка тянется заново).
- Отчёт: `akit analysis report [BATCH] [--compare BATCH]`.
- Проверки и судьи: `akit analysis check [MODE…]`, `akit analysis judge enable|disable|run MODE`, `akit analysis validate MODE dev|test`, `akit analysis validation [MODE]`, `akit analysis tough MODE SESSION present|absent`.
- Фиксы: `akit analysis fix draft|applied|show|status MODE …`.
- Контроль: `akit analysis control task new|check|remove …` (задача из коммита: `task new --commit SHA [--repo DIR]`; у любой формы `task new` есть `--layer-set СЛОЙ`), `akit analysis control tasks`, `akit analysis control run …`, `akit analysis control compare …`.
- Наборы слоёв: `akit analysis control layer-sets`, `akit analysis control layer-set СЛОЙ [add|remove ЗАДАЧА[,…] | answer ПОЛЕ=ЗНАЧЕНИЕ… | delete]` (`ПОЛЕ=` убирает ответ).
- Политика: `akit lab policy`, `akit lab policy check|allow|remove|pi-account|limit …`, `akit lab sends`.
- Разбор: `akit lab new review SESSION [--harness pi] [--model M] [--mode call]`, `akit analysis notes [SESSION]`.

### Что есть только в CLI

- `akit sessions import` — наполнение индекса (в приложении кнопки нет).
- `akit insights install` — хук захвата (HEAD в начале сессии) и ежечасный импорт.
- `akit analysis signals` — пересчитать сигналы всех сессий индекса вручную (пакет делает это сам перед выборкой). Сигналы одной разобранной сессии показывает окно заметок сессии.
- `akit analysis check` с отклонёнными и слитыми режимами: **Run All Checks** берёт только текущие.
- `akit analysis unclear SESSION#NOTE` для любой заметки.
- Команды, которые отправляют данные модели (`cluster`, `retro`, `route`, `bootstrap pair|first-modes|notes|similar`, `judge run`, `validate` с судьёй, `control run`), без `--yes` только печатают размер и оценку (у `control run` — число ячеек и оценку). Чтобы отправить или поставить в очередь, повторите с `--yes`.
- `notes`, `signals`, `check` и все подкоманды `control`, кроме `run`, ничего не отправляют и отказываются от `--harness`, `--model`, `--effort` и `--yes`, а не молча их игнорируют.
- `akit lab policy check HARNESS --model M` — проверка аккаунта с другой моделью (**Check Accounts** берёт модель по умолчанию).
- `akit analysis bootstrap label …` — дополнить законченную разметку, не открывая её заново (в приложении — **Reopen for Editing…**).
- `akit analysis control run … --no-start` (тоже только с `--yes`) и прочие флаги запуска: `--setups`, `--patch-text`, `--patch-file`.

## Частые сообщения и что делать
<!-- section: problems -->

### «… didn't produce this data (…). This is a work Mac: allow other destinations only as your company's policy says…»

Рабочий Mac, и данные пришли не от этого агента и провайдера. Например, сессию Claude Code шлют в Pi. Выберите агента, который записал сессию: ему данные отправляются без списка. Либо, если правила компании разрешают, добавьте адресата: Settings → **Check Accounts** → **Add to List** или **Add Destination…**.

### «… didn't produce this data (a Claude Code session). Add it to the allowed list…»

Личный Mac, но адресат не тот, кто создал данные. Например, сессию Claude Code шлют в Pi. Добавьте адресата в список или выберите харнесс-источник. Сессия Pi, в которой ответы шли через нескольких провайдеров, не имеет одного источника: такую можно отправить только адресату из списка.

### «… Pi can't tell which X account it uses: allow it once…»

Данные чужие для Pi (например, сессия Claude Code или сессия Pi через нескольких провайдеров), а Pi не говорит, под каким аккаунтом он вошёл к провайдеру X. Один шаг: **Add Destination…** → **Harness** Pi, **Provider** X, ваш логин и план или организация (для GitHub Copilot — организация, которая его выдаёт). Запись попадает в список разрешённых и становится аккаунтом Pi для X. То же в терминале: `akit lab policy allow pi X ЛОГИН ОРГАНИЗАЦИЯ`. На рабочем Mac добавляйте адресата, только если правила компании разрешают отправлять ему данные сессий. Сессию Pi тот же провайдер разбирает без всякой записи.

Окна разбора (**New Run…**, **Review in Terminal…**, **Re-check with Another Model…**, **Review with a Model** на вкладке **Bootstrap**) показывают это ещё до запуска: оранжевая строка «Not allowed: …» под полями агента и кнопка **Add Destination…**, в которой агент и провайдер уже заполнены.

### «Pi isn't signed in to X (pi auth check: …)»

Войдите в Pi к этому провайдеру (`/login` в Pi), затем **Check Accounts**.

### «Claude Code is not signed in» или «claude auth status names no organization …»

Войдите в Claude Code. Без организации или плана вызов отклоняется: AKit не может проверить политику.

### «The session index is empty. Run akit sessions import first.»

Выполните `akit sessions import`. О том же сообщения «No indexed sessions to check. Import them with akit sessions import (or akit insights install for an hourly import).» (после **Run Check**) и «… isn't in the session index. Import sessions with akit sessions import first.» (при создании контрольной задачи). Кнопки импорта в приложении нет, используйте команду.

### «No sessions match (at least 5 requests each)»

Фильтр пакета слишком узкий, или все подходящие сессии зарезервированы или лабораторные. Расширьте период или выберите **All projects**.

### «Not sent: the monthly limit is …»

Лимит месяца будет превышен. Поднимите его в Settings или подождите следующего месяца. Пакет проверяет лимит при постановке: если оценки нет, проверяется только уже потраченное.

### «no estimate yet (no recorded calls of this model)»

Эта модель ещё ничего не записала в журнал. Разберите одну сессию этой моделью. Оценка появится и в пакетах.

### «This session is reserved for bootstrap labeling; review it after you have labeled it.»

Разбор отклонён при запуске. Разметьте сессию на вкладке Bootstrap и нажмите **Finish…**.

### Матрица скрыта

«Hidden: no bootstrap phase agreement for … yet» — для версии заметок этого пакета нет подтверждённых пар, или в подтверждённых сессиях ни разу решающий шаг не указали и вы, и модель. Разметьте (с решающим шагом), поставьте **Queue Model Notes…** той же моделью, подтвердите пары. «… below 70%» — модель плохо попадает в фазу решающего шага: матрице по её шагам верить нельзя.

### «Fewer than 50 sessions of this project in batches» и воронка

Мало данных для матрицы 6×7. Гоняйте ещё пакеты с тем же фильтром проекта.

### «Seen in k notes» вместо процента

У режима нет точной или провалидированной проверки. Для механической проверки нажмите **Run Check** и подождите следующий пакет. Эвристическую код-проверку можно провалидировать и без судьи (**Validate on Dev…**, затем **Validate on Test…**). Для режимов без код-проверки нужен судья. В обоих случаях — 30+ тестовых меток каждого класса.

### «Below detection threshold»

Проверка ложно срабатывает так же часто, как наблюдаемая доля. Нужна более точная проверка (выше TNR).

### «The test set already ran for … with this check»

Тест разрешён один раз на версию режима и проверку. Итерируйте на dev. Новый тест после смены определения, харнесса, модели или промпта судьи, или версии код-проверки.

### Валидация: «N tough calls left out» или «N labels without a verdict»

Сложные случаи судьи решаются в блоке **Tough calls** на вкладке Review (**Present** / **Not Present**) или командой `akit analysis tough MODE SESSION present|absent`. «Без вердикта» у эвристической проверки — нажмите **Run Check**. У судьи — вызов по сессии не удался или транскрипта сессии больше нет. Приложение ошибки по отдельным сессиям не показывает; чтобы увидеть каждую, выполните `akit analysis validate MODE dev --yes`.

### «Made for vN; the mode is vM now. Run it again.»

Определение режима менялось после прогона проверки. **Run Check**.

### Кнопки судьи серые

Серыми бывают только **Enable Judge…** и **Change…**: режим среди активных не в тройке ни по заметкам, ни по цене заметок (токены или шаги), или у него нет фикса в статусе `draft`/`applied`. Сделайте черновик фикса (**Draft Fix…**). **Disable**, **Run Judge over the Pool…** и валидация этим правилом не ограничены.

### «Session … is in a test set; it can't be an exemplar»

Сессия попала в тестовый набор какого-то режима. Выберите другую заметку.

### «The fix of … was applied already; starting over would move T»

T уже стоит. Нажмите **Edit Draft…** → **Start Over…**, если действительно хотите начать заново.

### «The worker paused the batch: The account changed to … during the batch.»

Во время пакета сменился аккаунт харнесса (или перестал определяться). Верните аккаунт или разрешите новый, затем **Resume**.

### «The end of the batch failed: … Resume the batch to try again.»

Код-проверки, кластеризация или повышение не прошли. **Resume** доделает только конец.

### «The notes answer isn't the JSON asked for» и похожие

Модель ответила не по схеме. Сессия пакета получает статус `error`: **Retry Errors**. Если повторяется, выберите другую модель.

### «The akit command is not installed» или «… is older than this AKit»

В папке AKit выполните `make install-cli`.

### «No HEAD was recorded at the start of …»

Хук захвата не стоял, когда шла сессия. Напишите воспроизведение (**Reproduction…**) и поставьте `akit insights install --yes` на будущее.

### «The tests of … fail on its reference commit»

Исправьте команду тестов или reference, затем **Check Reference**. До этого **Run Cells…** не поставит ячейки.

### «No finished cells yet»

Ячейки в очереди или идут (Lab выполняет запуски по одному), либо их ещё никто не ставил: тогда сообщение добавляет «Run Cells… queues them in the Lab».

### Кнопки разбора нет у сессии Pi

Кнопка на экране Sessions и список в **New Run…** → **Review a Session** — только для Claude Code. Сессии Pi попадают в анализ через пакеты и через **Review with Model…** на вкладке Bootstrap.

### Разбор прошёл, а заметок нет

Проверьте **How**: нужен **One model call**. Режим **Agent with file tools** заметок не пишет.

### «A later review of this session replaced its notes»

Сессию разобрали ещё раз (например, **Re-check with Another Model…**). В пуле теперь заметки нового разбора; **Show Review** открывает его.

## Словарь
<!-- section: glossary -->

### Термины

- **Note (заметка)** — одна проблема в одной сессии: описание, шаг `#n`, цитата. Пишет модель (`n1`, `n2`…) или вы (`h1`, `h2`…).
- **Pool (пул)** — все разобранные сессии и их принятые заметки.
- **Accepted / rejected note** — заметка, принятая или отклонённая проверяющим. В пул идут только принятые.
- **Verifier (проверяющий)** — второй проход после заметок: код проверяет цитату, модель — утверждение.
- **Steelman** — сильнейший аргумент «проблемы здесь нет», который проверяющий пишет для заметок высокой серьёзности до вердикта.
- **Severity** — low, medium, high.
- **Fault layer (слой вины)** — agent (решения модели), harness (CLAUDE.md, скиллы, хуки, MCP), environment (инструменты, машина, сеть), task spec (запрос), grader.
- **Symptom of** — заметка-следствие другой заметки.
- **Requirements** — требования задачи, выписанные моделью из реплик пользователя до заметок.
- **Outcome (исход)** — achieved, partly, not achieved, unclear: достигла ли сессия цели, по тому, что видел пользователь.
- **Decisive step (решающий шаг)** — примерный шаг ошибки, которая решила исход.
- **Observed step (наблюдаемый шаг)** — первый момент, когда проблема стала видна.
- **Phase (фаза)** — Understand, Explore, Plan, Edit, Verify, Report. Explore, Edit, Verify и Report считает код; Understand и Plan может пометить модель.
- **Mode (режим)** — повторяющийся шаблон с определением и критериями include/exclude. Виды: failure, efficiency, success.
- **Seed (семя)** — один из девяти заранее заданных режимов (из исследований или наших наблюдений). Начинает неактивным.
- **Candidate (кандидат)** — режим, предложенный кластеризацией. Ждёт подтверждения или второго независимого случая.
- **Emergent** — режим, найденный в ваших заметках.
- **Umbrella (зонтик)** — слишком широкое семя: забирает больше 30% заметок.
- **Exemplar (пример)** — цитата, показывающая режим. Не больше трёх; идут в каждое сопоставление.
- **Route (маршрут)** — куда отнесена заметка: режим или «ничего не подходит», с уверенностью и источником (matching, clustering, retro, human).
- **None fits** — явный ответ «ни один режим не подходит».
- **Low confidence** — маршрут с уверенностью ниже 0.6: ждёт вас на Review.
- **Route acceptance** — доля проверенных вами маршрутов, которые вы приняли.
- **Matching (сопоставление)** — маршрутизатор «заметка → режим». Ведёт список, частоты не даёт.
- **Clustering (кластеризация)** — группировка заметок без режима в кандидатов.
- **Retro-matching** — сопоставление всего пула с одним режимом.
- **Unclear** — корзина заметок, которые вы не смогли отнести.
- **Check (проверка)** — вердикт «есть / нет» по каждой сессии для одного режима. Единственный источник частот.
- **Mechanical check** — код-проверка, совпадающая с определением режима. Точна по построению.
- **Heuristic check** — код-проверка, приближающая смысловой режим. Требует валидации.
- **Judge (судья)** — LLM-проверка одного режима по транскрипту.
- **Tough call** — пограничный вердикт проверки; без решения человека не входит в TPR/TNR.
- **TPR** — доля сессий с режимом, которые проверка поймала.
- **TNR** — доля сессий без режима, которые проверка верно пропустила.
- **Train / dev / test** — разбиение меток 10/30/60. Dev — для итераций, test — один раз.
- **Validated / provisional / exact / not validated** — уровни доверия к проверке.
- **Wilson interval** — интервал для доли, хорошо работающий на малых выборках.
- **Rogan–Gladen** — поправка наблюдаемой доли на TPR и TNR проверки.
- **Below detection threshold** — доля не выше ложных срабатываний проверки.
- **Bootstrap (стартовый набор)** — ваши слепые заметки на 30+ сессиях; единственное место, где меряется полнота модели.
- **Bootstrap (статистический)** — пересэмплирование для интервалов и парного сравнения. Не путать со стартовым набором.
- **Reservation (резерв)** — сессия, отложенная для слепой разметки; поштучно её не разбирают, пока вы её не разметите, а в пакеты не берут никогда.
- **Pairing (пары)** — сопоставление ваших заметок и заметок модели про одну проблему.
- **Recall (полнота)** — доля ваших проблем, которые нашла модель.
- **Precision (точность)** — доля принятых заметок модели, с которыми вы согласны.
- **Mapping** — сопоставление ваших заметок стартового набора с режимами; делает их метками.
- **Similar cases / finds** — находки модели, похожие на ваши заметки режима; ваше решение — дешёвая метка.
- **Stop rule** — остановка стартовой разметки после 20 размеченных сессий без изменения списка режимов.
- **Notes version** — харнесс · модель · версия промпта заметок; полнота и совпадение фаз меряются для каждой отдельно.
- **Batch (пакет)** — Lab-запуск над выборкой сессий: заметки, проверка, сопоставление, судьи, в конце кластеризация.
- **Stratum (слой)** — группа выборки: харнесс | семейство модели | сильнейший сигнал.
- **Signals (сигналы)** — дешёвые признаки сессии, считаемые кодом: прерывания, протесты пользователя, отказы в вызовах, ошибки инструментов, повторы вызовов, «готово» без проверки, длина. Сессия с отказом попадает в слой `pushback`, как и сессия с прерыванием или протестом.
- **Inclusion probability (π)** — вероятность, с которой план выборки берёт сессию; из неё вес 1/π.
- **Horvitz–Thompson** — взвешивание по 1/π, возвращающее выборку к пропорциям всех сессий.
- **Coverage** — сколько сессий пакета готово из всех.
- **Saturation (насыщение)** — новые режимы перестали появляться.
- **Transition matrix** — таблица «фаза перед решающим шагом × фаза решающего шага».
- **Funnel (воронка)** — решающие шаги по фазам, вместо матрицы при малом числе сессий.
- **Done key (ключ готовности)** — хеш входа и настроек шага; если он есть, шаг не повторяется.
- **Digest (дайджест)** — сжатый транскрипт, который читает модель: реплики пользователя целиком, длинный вывод с началом, концом и ошибками.
- **Scrub (маскирование)** — замена секретов, хостов, e-mail перед отправкой.
- **Sending policy** — правила, куда можно слать данные сессий и код.
- **Same origin** — правило личного Mac: данные можно слать тому, кто их создал.
- **Allowed list** — явно разрешённые адресаты (харнесс · провайдер · аккаунт · план/организация).
- **Send log** — журнал всех отправок с записанной стоимостью.
- **Fix (фикс)** — изменение настройки против режима: open → draft → applied(T) → confirmed / didn't help / rejected.
- **T** — момент, когда вы применили фикс; граница «до» и «после».
- **MDE** — минимальный заметный эффект при данном числе сессий.
- **Control task (контрольная задача)** — промпт на коммите репозитория с оракулом.
- **Oracle (оракул)** — тесты проекта или код-проверка режима на транскрипте ячейки.
- **Reference** — коммит, где тесты должны быть зелёными.
- **Cell (ячейка)** — один прогон агента на одной задаче в одной настройке.
- **Setup** — baseline (как есть), variant (ровно одно отличие), read-only (проверка, что оракул работает).
- **Guard flags** — признаки, что ячейке нельзя верить: тестов стало меньше, тестовые файлы изменены, агент читал исходную сессию.
- **pass@1** — шанс, что один прогон пройдёт.
- **pass^k** — доля задач, где прошли все k прогонов.
- **Lab run** — запуск в Lab: разбор, повтор коммита, пакет или ячейка.
